# Step 4d5 follow-up review R1: stored-projection import boundary

## Summary

This delta fixes a problem that showed up once the tests used a real save and reload. The existing persistence policy saves Claude Read tool rows in summarized form, so after a reload the exact Step 4d3a payload check reports them `unavailable`. That refused every later import of the conversation. The fix adds an import-only fallback in `canonicalPayloadRefusal`. A ledger row may still be accepted if all of these hold:
- the reader marks it as a singleton Read exchange;
- exactly one ledger entry maps its key and exactly one maps its local item ID;
- that entry has a non-nil digest that equals the native entry's digest;
- it has exactly one full, uncompacted backing activity.

Both the backing and the suffix copy must then each match one whole representation out of at most four, generated by the current pipeline from the native projection: loaded, loaded-hidden, rebuilt and rebuilt-hidden.

Other changes:
- **Cold restore:** it now receives the Claude-associated local IDs and skips only the synthetic cancel/error/result rewrite for those rows. The turn, span, interruption and terminal handling is unchanged.
- **Live owner:** a duplicate Read answer is now detected anywhere in the canonical view. The single-text Step 4d3b path keeps its suffix-only check.
- **Unidentified result rows:** they now carry the matched call's arguments.
- **Tests:** they now use real relaunch compositions (new store, service, coordinator and view model on the same roots), two save/hydrate/reconcile cycles, a call-only cold restore, partial-history continuation, and whole-representation membership checks.

I found no P0 or P1. The fallback adds no new authority: acceptance always depends on an existing, unique, digest-matching ledger proof. Nothing is minted from a stored form, the live `holdsCanonicalPayload` check is still exact, and imports change no storage, ownership or accounting. The remaining issues are about how complete and durable the four-form set is, one activation-time hazard, and test fidelity.

## Findings

### P2

**P2-01: The four-form set depends on the code version, so a later policy change turns valid stored rows into a permanent `canonicalPayloadMismatch`**
- **Scenario:** a session saved now holds proven Read rows in today's summarized form. Later, the owner changes any part of the persistence or runtime sanitizer: summary wording, `minimalResultJSON` shape, render summary, or `summaryOnly`/status handling. On the next import into that conversation, `storageComparisonActivities` regenerates only the *current* forms. The old backing matches none of them, and `compareStoredProjection` returns `.mismatch`. The payload check runs over every ledger row of the conversation, so all future imports for that conversation are refused, and the refusal reads like tampering. The existing round-trip tests produce both sides with the same code, so they will not catch this.
- **Impact:** product recovery imports for affected conversations break silently after an upgrade. It fails closed and no data is lost, but there is no recovery path.
- **Evidence:** `AgentProviderHistoryImport.swift:~718` (`guard backingMatches, suffixMatches else { return .mismatch }`) and `AgentTranscriptPolicyPipeline.swift:62-96`. The owner contract excludes historical versions.
- **Smallest fix:** commit one golden fixture: a session JSON with a stored singleton Read exchange from this build, plus a test that imports it with the current code. Any policy change then fails CI, and the owner decides about migration at that point. Optionally, when the backing is `summaryOnly` and matches no form, return `.unavailable` rather than `.mismatch`, so policy drift is not reported as altered content.

**P2-02 (activation gate): a cleared live proof poisons all later imports of the conversation once rows are saved summarized**
- **Scenario:** after activation, a qualified Read call and result are inserted live. The answer then arrives while the tab is in the background (`!isBackground` refuses), or any later link refuses. `refuseClaudeLiveTranscript` clears the proofs of the owned call and result. This is normal tab switching during a run. In the same launch, the raw suffix copies still compare exactly. After any reload they are summarized, so `comparePayload` returns `.unavailable`. The fallback requires `native.envelopeDigest` and gets nil, so the result is `.canonicalPayloadUnavailable`. That check covers every applicable ledger row, so every later import of that conversation is refused.
- **Impact:** this is not reachable today because no production producer is active. Once activated it would be a P1-class workflow break: interrupted runs in that conversation can never be recovered by import. This class of row is new with Step 4d5; text rows survive saves exactly and imported proofs are never cleared.
- **Evidence:**
  - `AgentProviderHistoryImport.swift:~544-556` (digest required for `stored`)
  - `AgentProviderHistoryImport.swift:~518` (all conversation rows compared)
  - `AgentModeViewModel.swift` `applyClaudeLiveTranscriptCompleteText` guard and `refuseClaudeLiveTranscript`
- **Smallest fix:** no code change in this step. Record it as an activation blocker in the plan's status. The design options are:
  - (a) limit stored-form comparison to rows that the dispatch window or boundary actually touches;
  - (b) accept that a refused chain makes the conversation non-importable, and surface that to the user.

**P2-03: Test gap: the continued partial-history state is never saved and relaunched**
- **Scenario:** in `testImportedReadRowsSurvive…` (call-only branch), the result and answer import after the protected call, with their own recovered system label between call and result. Then the test ends. The four forms are generated from an isolated `[call, result]` pair with consecutive sequence indexes. The real stored turn here is `call, label, …, result, answer`, assembled across two imports and a cold-restored (cancelled) turn. If the result's persisted summary or the call's execution depends on adjacency or pairing within the turn, the next relaunch import would refuse. That is exactly the boundary this round exists to cover.
- **Evidence:** `AgentRecoveryReconciliationTests.swift:~2700-2735`. There is no `relaunchAndReconcile` after `continued`.
- **Smallest fix:** add one save → `relaunchAndReconcile` → `.nothingImported` cycle after the continued import, with the exchange being the native call and result.

**P2-04: Test gap: realistic turn context outside the one-exchange fixture**
- **Scenario:** all real round-trip tests use one Read exchange per turn with no other activity between call and result. Real O20 turns often have several singleton Read exchanges, or an `assistantInline`/thinking row between `tool_use` and `tool_result`. The generated forms are produced in isolation (`storedReadImages` → `storageComparisonActivities`). Whether the real stored or hydrated backing matches still depends on what surrounds the row: turn terminal state, visibility from later rows, grouped history refresh.
- **Impact:** a missed form fails closed (refusal), but it breaks the exact case the fix targets.
- **Evidence:** `AgentTranscriptPolicyPipeline.swift:62-80` builds with `terminalState: nil` and only the exchange's rows. `deliverLiveReadChainAndSave` uses one exchange.
- **Smallest fix:** extend `o20History` with a second singleton Read, or an inline text between call and result, in one turn. Run the existing two-cycle relaunch for both the terminal and running cases.

**P2-05: The privacy assertion cannot see a partial leak because the output token equals the answer**
- **Scenario:** `assertStoredSummarized` checks only that the bytes do not contain `1\tBRAVO-42`. The Read output and the reply are both `BRAVO-42`, so the test cannot check for the bare token. A summary or preview that kept a reformatted snippet of the output (e.g. `BRAVO-42` without the line-number prefix) would pass. The owner asked that fixtures not hide privacy gaps.
- **Evidence:** `AgentRecoveryReconciliationTests.swift:~2476`. `deliverLiveReadChainAndSave` uses `output = "     1\tBRAVO-42\n"` and `reply: "BRAVO-42"`.
- **Smallest fix:** add a sentinel to the fixture output that appears only there (e.g. `"     1\tBRAVO-42\n     2\tOUTPUT-ONLY-SENTINEL\n"`). Assert that the stored bytes never contain `OUTPUT-ONLY-SENTINEL`.

### P3

**P3-01: The cold-restore `protectedItemIDs` parameter defaults to `[]`**
- Any other caller of `sanitizeColdRestoredTranscript`, now or later, silently gets the old behavior and cancels/errors a protected call alone. That would break the next import with `.mismatch`.
- **Evidence:** `AgentSessionRestoreSupport.swift:530`.
- **Fix:** remove the default so every call site must choose (only `AgentSessionDataService.swift:~890` passes it today).

**P3-02: The "held only in persisted turns" live test builds an unreachable state**
- `buildTranscript(…, compact: false)` puts *raw* tool rows in turns with an empty suffix. On a real load, full turns are mirrored into the suffix and tool rows are summarized. Turn-only rows exist only in non-full turns, which are `unavailable`.
- The new `!prerequisites.isEmpty` duplicate branch is harmless, but the test name claims coverage of a path that real storage cannot produce.
- **Evidence:** `ClaudeNativeBackgroundTranscriptTests.swift:~2028-2046`.
- **Fix:** rename it, or note that it is an in-memory-only shape. After a real reload this path fails closed on the exact prerequisite check, which is the acknowledged mid-chain hydration case.

**P3-03: The "hidden" forms re-sanitize an already runtime-materialized transcript**
- `hidden(loaded)` runs the runtime sanitizer on `runtimeTranscriptOnly`'s output. The real path sanitizes the normalized stored transcript in a single stabilization pass. They are equal today (the tests prove it for one exchange), but only because sanitizing twice happens to be idempotent.
- **Evidence:** `AgentTranscriptPolicyPipeline.swift:~74-80`.
- **Fix:** add a one-line comment stating that assumption. Optionally, assert idempotence in the pure test.

**P3-04: Per-import cost grows with the number of proven Read exchanges**
- After a reload, every proven singleton Read row falls back, and each exchange runs a full build → persist → two runtime stabilizations → rebuild → two sanitizations. That is O(exchanges) per import on the reconcile path. It is negligible now (default off), but it grows after activation. Advisory only.
- **Fix (if it shows up):** only generate forms for rows whose backing is `summaryOnly`. The `storedImagesByInvocation` cache already avoids repeats within an exchange.

**P3-05: The cold-restore test fixture uses `rowKindRaw: "assistant"` for a tool-call ledger entry**
- This works only because `claudeLocalItemIDs` ignores the kind.
- **Evidence:** `AgentRunTerminalCauseTests.swift:~250`.
- **Fix:** use `ClaudeSessionHistoryReader.RowKind.toolCall.rawValue`.

**P3-06: `assertGeneratedRepresentations` copies the production `sameProjectedTool` predicate**
- If the predicate has a bug, the test has the same bug.
- **Fix:** acceptable for an oracle check. Also add one assertion that compares the backing's `toolExecution.summaryText` and `resultJSON` to literal expected strings, so at least one check is independent of the code under test.

## Is the bounded four-form contract sound?

**It adds no new authority. Yes:**
- **Authority still comes only from the ledger.** The fallback runs only after the exact comparison says `.unavailable`. It also requires one applicable ledger entry per key and per local ID, a non-nil digest equal to the current native entry's digest, and a validated singleton Read shape (`storageComparableReadItemIDs` checks the canonical input JSON, a single-row entry, at most one result, and no `is_error`).
- **No forms are mixed.** The backing must equal one whole generated activity (kind, text, complete `toolExecution`, and projected fields). The suffix copy is matched to a whole form on its own. Mixed-field tampering is tested.
- **Nothing is minted.** Observation rows that are already present but not in the ledger get no `stored`, so a summarized copy can never gain a new ledger entry or digest through the planner's "record, do not duplicate" branch.
- **The live path is unchanged.** `holdsCanonicalPayload` stays exact, and the tests confirm a stored copy is never "held".
- **Cold-restore protection is narrow.** Only the synthetic rewrite of protected rows is skipped. A test shows that everything else in the turn equals the unprotected restore.

**Where it is weaker:**
- **The set is complete only by test, not by construction.** It is generated in an isolated, terminal-state-free context, so any real context that changes the stored form makes the import refuse (P2-03, P2-04).
- **It is tied to the current code version** (P2-01).
- **Lossy summaries mean acceptance relies on the in-memory mutation guards plus the digest,** not on the payload itself. That fits the contract but should be stated.
- **The fallback rescues only singleton Read.** Any other imported tool shape (parallel or multi-block entries, Bash, Edit, Grep), and any cleared-proof row (P2-02), still blocks every later import of its conversation after the first save. The deferred "wider tool shapes" item therefore covers more than polish.
