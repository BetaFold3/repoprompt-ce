## 1. Outcome and scope

Make three bounded improvements without replacing the runtime:

1. Prefer event-driven waits over repeated polling in workflow guidance.
2. Add trustworthy cache-read-share and cost readouts for both native Claude and Codex: provider-reported estimates for Claude, locally calculated API-equivalent token estimates for Codex.
3. Offer opt-in assistant-result trimming with exact, authorized recovery.

The earlier decision to keep one numeric **120-second** wait default is superseded by the implemented Phase 7 policy (§6). Omission remains visibly **automatic** and resolves once from the frozen effective parent provider family and launch-resolved retention: **180 seconds for Claude, 1500 seconds only for Claude with explicit effective one-hour prompt-cache configuration, 600 seconds for Codex, and 180 seconds for every other or unresolved parent**. This operational mapping is not a promise about any provider's cache lifetime. Event-driven completion and interaction wakes remain early; explicit caller timeouts remain authoritative within the new four-hour server maximum.

The recommended first release uses a **separate session-owned usage record with turn summaries, Claude cumulative-cost checkpoints and Codex locally priced usage intervals**. It does not repurpose context estimates as billing data. Request-level diagnostics use bounded opt-in existing event capture and offline analysis, not a new live diagnostic UI or persisted request-history ring.

Non-goals: child-to-parent push; changing provider cache TTLs, credentials, subscriptions or permissions; provider-native zero-output keep-alive requests; automatic parent-plus-workers UI totals; numeric accounting for unqualified providers; general persistence/runtime refactoring; changes to release metadata. No source behavior is changed by this document.

The projection accepts only an active-session-owned, semantically valid record with matching origin; unsupported opaque values and foreign-origin records remain unavailable. This does not qualify live accounting. Codex remains explicitly unavailable because Phase 2b is deferred, and other providers show unavailable rather than inferred numeric values.

To avoid repeatedly deriving validated projections on the main actor, each `TabSession` caches its sidebar projection. Its key covers the selected provider, expected and accounting owners, qualification, eligibility, owned accounting revision, active execution and an explicit accounting-replacement generation. `replaceUsageAccounting` invalidates the cache and advances that generation, so same-owner hydration or replacement at revision zero cannot reuse an older projection. | Boundary | Implemented contract |
|---|---|
| Transport | `result_index` and `queued_turn_count` are preserved on the package/core usage observations (`.result` only, `observedCount` strictness, zero stays zero, booleans stay missing) and mapped in both bridge directions. |
| Process launch identity | `ClaudeNativeProcessSessionController.ProcessLaunchIdentity` (token, PID, fresh/resumed mode, command provenance, runtime variant, resolved and real executable paths, backend, environment evidence) is created at successful spawn. Environment evidence (`launchEnvironmentEvidence`) is derived from the final dictionary handed to `ProcessLauncher.spawn`, never from resolver intent alone: `environmentOverrideKeys` lists every resolver override/removed key plus every backend-routing key (`ANTHROPIC_*`, `CLAUDE_CODE_USE_*`, `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`) present in the child environment whatever its origin (inherited login shell, configured override or resolver), and `configuredEnvironmentOverrideKeys` lists the app's own `config.processEnvironmentOverrides` keys (the Agent Mode shape is `MAX_MCP_OUTPUT_TOKENS`, `MCP_TIMEOUT`, `MCP_TOOL_TIMEOUT`; discovery launches carry none). | Dispatch registration | After a successful stdin write the controller registers the turn and a launch-local zero-based ordinal in the same non-suspending actor step. |
| Result attribution | A raw `result` is attributed only when, on the current launch, an unblocked state holds runtime-version evidence, the result's `session_id` equals the launch's provider session, `result_index` is a valid integer equal to the next unattributed ordinal, and a dispatch exists for that ordinal. ## 4. Accounting and display contracts

### Claude tokens

Request observations are snapshots/upserts, not additive events. Missing fields do not erase earlier fields; duplicates do not increase totals. Main-loop and native-sidechain scopes stay distinguishable.

For an accepted authoritative turn result, use its qualified main-loop totals instead of adding them to request subtotals. Before such a result, deduplicated observations can provide a partial subtotal. Output placeholders must not be promoted to finalized billed output.

CH is the token-weighted share:

```text
sum(cache read) / sum(uncached input + cache read + cache creation)
```

Only complete, validated input triples contribute an unqualified ratio. Excluded or unmeasured intervals make displayed coverage partial. A zero denominator is unavailable. Never average request percentages, use context occupancy as the denominator, or present high CH alone as proof of savings.

### Claude provider-reported cost

Within a qualified segment, replace the latest checkpoint:

```text
segment contribution = latest accepted cumulative estimate - known segment baseline
session estimate = sum(disjoint owned segment contributions)
```

Results 1.00 then 1.50 mean 1.50, not 2.50. Keep raw precision until display.

- Zero baseline requires a verified query-start contract.
- A same-provider-session resume may create a new query execution. Never subtract the RPCE lifetime total from a provider query counter.
- With unknown historical baseline, mark prior coverage unmeasured; do not charge the first observed cumulative amount as newly incurred work.
- A reset generation changes only on a positively verified reset boundary, not on a counter drop, compaction or MCP epoch transition.
- Ignore identified stale/duplicate events. An unexplained later decrease suspends the segment as partial; do not infer a reset.
- Valid original error results may report usage. Cancellation/crash without a final result preserves accepted checkpoints and explicitly incomplete coverage; a zeroed crash report cannot erase earlier accepted spend.
- A cost-only report can be meaningful even when the context estimator would append nothing.

First-party native Claude uses this monetary contract. Its cost includes native subagents; CH describes its main loop. Separate RPCE worker sessions are excluded from the parent's figure. #### Arithmetic and display

For qualified observed intervals, let I be total input, C cached input, W cache-write input and O output inclusive of reasoning. Validate nonnegative integer counts, C+W <= I when all are known, and overflow-safe arithmetic. The official [prompt-caching arithmetic](https://developers.openai.com/api/docs/guides/prompt-caching) treats read/write counts as input subsets. The installed app-server must still preserve those meanings.

```text
CH = sum(C) / sum(I)
ordinary input = I - C - W
API-equivalent token estimate =
    (ordinary input * inputRate
     + C * cachedInputRate
     + W * cacheWriteRate
     + O * outputRate) / 1,000,000
```

Rates are Decimal; round only presentation. Do not add reasoning output a second time. CH can be available while cost is partial; missing is distinct from zero and a zero input denominator is unavailable.

Unknown `W` (review R1, 2026-09-15): an absent `cacheWriteInputTokens` is never normalized to zero. With a listed write rate the interval is a range over the corners `W = 0` and `W = I − C`; without one it is an explicitly partial subtotal of cached and output tokens only (interval coverage partial, diagnostic names the excluded input tokens). Only an explicit `W = 0` yields a point. Range readouts round the lower bound down and the upper bound up. Absolute counters must be non-negative and `C + W <= I` is validated independently of pricing: inconsistent intervals keep their counts, stay unpriced/partial and are excluded from CH. Monotonicity is checked against the latest accepted checkpoint before any same-turn refinement baseline; a notified observation for an already settled turn is rejected as replay with no state change. A reroute invalidates every priced interval of that execution and turn (counts preserved). Checkpoint ownership is ordered by `turn/started` binding order, independently of whether a turn ever reported usage (review R2): a notified observation for a turn bound before the turn that owns the latest accepted (or prospective) checkpoint is demonstrably older — its first report arrived late — and is rejected with no state change, never rebaselined, so a later turn's interval can never overlap it (its work stays inside the later accepted interval; coverage partial/unavailable, never a double count or a refund). The refinable checkpoint (`openTurn`) moves only on accepted usage: unmeasured-work markers are tracked apart from it, so closing another turn without usage never revokes the open turn's provable refinement ownership, and a late report for a marked turn replaces its marker in place from the current checkpoint.

Use **Standard/global list-price equivalence** for all requested tiers, including Fast, as a stable comparison basis—not a reconstruction of subscription charges, actual service tier, regional uplift, tool fees or invoice adjustments. Preserve those exclusions/assumptions in tooltip and persisted provenance. This also means the figure alone cannot establish actual billed savings across providers with different monetary scopes.

Presentation ladder:
1. A point estimate when supported pricing dimensions and counters are known.
2. An explicitly conditional finite range when missing write counts or context bands have proven bounds. If W is unknown and I/C are qualified, its possible interval is 0 through I-C. Use conservative category-rate envelopes across eligible context bands that cover mixtures of requests; simple corner calculations are allowed only when tests prove they bound those mixtures. Round displayed lower/upper ends outward. No midpoint or unjustified greater-than-or-equal label.
3. An explicitly partial subtotal of independently priceable components when bounds/rates are unknown, otherwise unavailable. Never pretend all I-C tokens are ordinary input if unknown W could occupy part of them.

An explicitly qualified non-applicable separate write charge differs from a missing rate, and does not by itself prove W=0. Missing context-band attribution does not justify silently using the cheaper band. Ranges bound the stated token-price assumptions, not the user's invoice.

## 6. Wait guidance and timeout policy

This section supersedes the numeric policy in the outcome, §2.7, §2.8, the Phase 5 row, G3's old rollout order and §9.6. It also supersedes the adaptive TTL design preserved as history in §9.9. Those dated sections remain intact as implementation history; the behavior below landed atomically in Phase 7.

### 6.1 Product policy and exact values

Treat an omitted lifecycle timeout as **automatic**, not as though the caller explicitly supplied one universal number. Resolve the automatic value once from the effective **parent** provider family:

| Effective parent provider | Automatic wait |
|---|---:|
| Claude Code (`.claudeCode`) without explicit effective one-hour prompt-cache configuration | **180 seconds** |
| Claude Code with explicit effective 1 h prompt-cache configuration | **1500 seconds** |
| Codex (`.codexExec`) | **600 seconds** |
| Every other named provider | **180 seconds** |
| No authoritative live parent, no unique match, remote/external caller, or other unresolved context | **180 seconds** |

“Parent” means the model invocation that called the MCP lifecycle tool, not the worker being started or observed. Do not infer it from the requested worker model, MCP client name, a role label, or whether some runtime happens to use a Claude-compatible protocol. In the current provider enum, only `.claudeCode` belongs to the Claude row and only `.codexExec` belongs to the Codex row; `.openCode`, `.cursor`, `.ohMyPi`, `.claudeCodeGLM`, `.kimiCode`, and `.customClaudeCompatible` deliberately use the other-provider fallback.

Centralize the family enum, resolver and numeric values in `MCPTimeoutPolicy.swift`. The required constants are:

- Claude automatic wait: **180 seconds**;
- Claude extended-cache automatic wait: **1500 seconds**;
- Claude Code default stdio MCP tool idle abort: **1800 seconds** (documented host default; CE does not override it);
- Claude host pre-wait budget: **60 seconds** for readiness, preflight, and packaging;
- Codex automatic wait: **600 seconds**;
- other/unresolved automatic wait: **180 seconds**;
- maximum automatic wait: **1500 seconds**;
- owned waiting-operation response envelope: **1530 seconds** (1500 + 30);
- maximum explicit lifecycle timeout: **14,400 seconds**, exactly four hours.

**Amendment (2026-09-24).** The extended Claude row is selected only from positive explicit evidence in the final process launch environment and Claude settings precedence (managed, project-local, project, then the effective user settings path). Visible launch-environment and effective settings-environment values for `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` and `MCP_TOOL_TIMEOUT` also conservatively disable the extended row when invalid or below the required automatic-wait-plus-response-margin-plus-60-second-pre-wait budget; a zero Claude idle timeout is treated as disabled. Resolution happens once per parent process launch, is copied through the live parent session, and is frozen with the lifecycle `RequestContext`. The 1500-second value is a deliberate operational heuristic chosen relative to an explicitly configured one-hour cache—an exception to the general not-TTL-derived rule—but it adds no runtime TTL qualification or cache-age machinery. Claude Code's documented default `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` aborts a silent stdio MCP tool call after 1800 seconds, and CE neither overrides that launch variable nor sends progress notifications to Claude Code, so the extended automatic wait is limited to 25 minutes to preserve response margin inside the host idle window. Explicit timeouts above approximately 1710 seconds (1800 minus the 30-second response margin and the 60-second pre-wait budget) from a Claude parent can already be cut off by that idle window, and CE's 10,800,000 ms `MCP_TOOL_TIMEOUT` launch override is below the 14,400-second explicit maximum; these pre-existing limitations are not changed here. The canonical `wait_policy` wire shape is unchanged and contains no retention or TTL field. The gateway still caps its response envelope at 900 seconds, so the shared 1530-second omitted-wait envelope clamps to 900 there. MDM/server-managed state not materialized in the managed-settings file, wrapper scripts that change `CLAUDE_CONFIG_DIR` after spawn, settings hot-reload after launch, and gateways or compatible providers that do not honor the TTL remain invisible; absence, invalid values, and unknowable subscription defaults resolve to standard retention.

Keep the public `agentLifecycleDefaultWaitSeconds` symbol as a compatibility alias for the 180-second fallback if removal would break callers. New provider-aware production code must not use that alias as a universal default. `AgentMCPToolHelpers.maximumTimeoutSeconds` must derive from the shared 14,400-second constant so schema text, parsing and transport tests cannot drift. The server accepts inclusive explicit values from **0 through 14,400 seconds** and rejects values above the maximum; it must not silently clamp them. Zero remains a non-blocking poll.

These constants are product policy, not dynamically discovered cache facts. In particular, the Codex value does not claim that Codex CLI/app-server inherits the Responses API's documented 30-minute option. The simplicity is intentional: when first-party product evidence or measured CE behavior changes, maintainers update one reviewed mapping and its tests rather than repairing TTL qualification, request-clock and cache-age machinery.

### 6.2 Wait semantics and model guidance

The selected timeout remains a **wait-phase** upper bound. Existing start or steer preparation does not consume it; `waitForInterestingState` starts one monotonic deadline when parking begins and does not restart it during status sampling. Completion, interaction, cancellation and other actionable state wake the continuation early. Reaching the timeout returns the existing state shape and does not cancel an accepted worker. A subsequent wait is normal.

Change the tool schema, CLI help, `WorkflowPromptSharedFragments.swift`, the five managed workflow owners (Investigate, DeepPlan, Optimize, Orchestrate and Refactor), and any conflicting lifecycle reminder text in `WorkflowPrompt+Reminder.swift` so routine supervision omits `timeout_seconds`. The guidance must state all of the following:

- omission selects the parent-provider default: Claude 180 seconds (1500 seconds when the parent's effective Claude configuration explicitly sets a one-hour prompt cache), Codex 600 seconds, other/unresolved 180 seconds;
- an early completion or interaction returns immediately, so the numbers are upper bounds rather than mandatory sleeps;
- the worker remains active after an MCP wait times out;
- a wait or transport heartbeat does **not** itself send a provider-model request and therefore does not warm a prompt cache;
- the next parent-model continuation may refresh a cache, depending on the actual provider product and account path;
- longer explicit waits trade fewer supervisory model calls against a greater chance of cache expiry on short-retention paths;
- explicit overrides are appropriate for a deliberate responsiveness/control trade-off or a known caller constraint, not merely because the worker may run for a long time;
- the accepted explicit range is 0…14,400 seconds, with zero meaning poll.

Do not claim that 180 seconds is universally “cache-safe,” that 600 seconds is a Codex TTL, or that a four-hour override is economically preferable only after some fixed worker-duration formula. Provider pricing and retention policies change, and Codex CLI/app-server behavior is not established by the Responses API page. The guidance should help the calling model choose consciously without pretending CE possesses a runtime TTL oracle.

Before a result exists, an omitted-timeout lifecycle call card shows the resolved numeric family upper bound only when the row belongs to the current-turn, full-retention, in-flight active run and its local owning session is authoritative: Codex shows `wait ≤10m`; Claude shows `wait ≤3m` or `wait ≤25m` for explicit effective one-hour prompt-cache configuration; every other named local provider shows `wait ≤3m`. Historical, archived, earlier-turn, unresolved and remote rows retain `wait auto`; remote presentation does not hard-code the unresolved three-minute server fallback. The parent is the calling/main agent, never the requested worker. Explicit positive values continue to show their numeric upper bound; zero shows poll, detached start shows detach, and non-waiting operations remain unchanged before completion. After completion evidence exists—either result JSON or a terminal error flag—a validated canonical root `wait_policy` exclusively owns the numeric or poll wait segment, including call rows produced by call-to-result mutation, while operation, session and model portions remain argument-derived. A detached start continues to show `detach` because it deliberately has no wait selection or `wait_policy`. Missing, malformed or legacy completion metadata yields no completed wait segment and never revives current context. Historical canonical automatic tuples remain authoritative when their family is known and their finite positive timeout is within the accepted bound, even when the value differs from today's family default. These presentation rules do not rewrite omission into an explicit timeout or change automatic result metadata.

### 6.4 Validation order, host coverage and gateway limits

### 6.5 Keep-alive scope and observability

Measurement can motivate a later constant change; it must not silently reinterpret a stored result.

This means a server-accepted explicit value above 870 seconds cannot receive its full wait plus 30 seconds through the gateway. One material disagreement survived the two-round limit:

- **Include a `version` field.** The argument is that provider classification, fallback rules or eligibility could change even when a stored tuple still says the same family and number. A version could tell future consumers which policy interpretation produced an idempotently replayed result.
- **Omit a `version` field.** The argument is that the tuple already records the complete observable selection needed by current consumers: mode, selected seconds and, for automatic mode, parent family. A version would become an opaque public contract unless the project also commits to immutable historical meanings, increment rules and migration behavior, none of which has a present consumer or acceptance requirement.

The plan adopts the second position for Phase 7: omit `version`. This is the orchestrator's recommendation, not claimed Oracle consensus. The result metadata reports the operational outcome rather than promising historical policy reconstruction, and avoiding a speculative field better matches the user's simplicity requirement. If a future consumer genuinely needs to distinguish policy generations, that follow-up must define version semantics, compatibility and tests before adding the field. No other material disagreement remains.
