# Codemap automatic convergence plan

Scope: read when the task touches automatic codemap convergence on large roots: demand release and the idle ready cache, projection source-authority batching, or automatic prompt-builder root repair.
Authority: Authoritative
Evidence: `docs/plans/evidence/2026-10-18-codemap-preload-churn/` (local).
Review policy: `docs/context/review-policy.md`.

## Problem (summary)
- Cause 1: external Git index rewrites leave the codemap authority baseline stale; prompt builders never repair it (only `get_code_structure` does).
- Cause 2: on a large root every automatic call restarts the whole projection (demand start/accept/release advance the overlay contribution generation; last-holder release also clears the root-wide published graph), and a full rerun costs ~400 s (16 git spawns per candidate). Release waits on the rerun, so calls can block for minutes.

## Steps
1. Release keeps ready codemaps warm and root graph state intact; bounded release wait (Oracle seams S1 + S2).
2. Projection issues source authority once per batch window (up to 128 candidates) instead of twice per candidate (seam S5b; no config memo).
3. Automatic prompt-builder operations use the existing bounded foreground root-session repair, without in-call restart (seam S6).
4. Contract doc update and owner live acceptance (dev-app rebuild/relaunch is owner-run).

Deferred by plan: semantic coverage advances (S3), incremental rerun (S4), and git config memo (S5a). Semantic index generation is implemented under D7; authority correctness and large-root convergence remain separate acceptance results.

## Decisions
- D1: implement the three-step fix (release/warm cache + bounded wait, batched authority windows, automatic foreground repair).
- D2: approve changing the contract so foreground automatic prompt builds may run a bounded repair; background work still never repairs.
- D3: add Step 1b (released, already-admitted pending automatic demands finish into the warm cache) if OracleA and OracleB approve; both approved with changes.
- D4: keep the DEBUG release-site counters for now; revisit when the plan is archived.
- D5: add Step 3b, a per-root cooldown on automatic root-session resets so periodic external index rewrites either let a rebuild finish or at least cap restarts, then rerun the live churn check.
- D6: the all-or-nothing `unresolved_reference` failure for multi-file selections goes to a separate follow-up plan.
- D7: Step 3b derives the index part of the repository authority from index entries (path, mode, blob ID, stage, assume-unchanged and skip-worktree flags) instead of index file metadata; the reset cooldown is deferred.
- D8: implement the Oracle-guided bounded correction with focused workers: truthful terminal automatic-projection reporting, generated-snapshot exclusion, focused regression and authority validation, then one bounded live acceptance without debugger or repeated polling. Preserve authority fences; do not add automatic rearming. A terminal-reporting pass does not establish convergence.
- D9 (OracleD/E-guided, 2026-10-20): the D8 zero-map state is a dead projection catalog token. Folder-only applied-index batches (FSEvents `folderModified` for a tracked directory whose changed entry is ignored or transient, such as `.DS_Store` or `__pycache__`) advance `appliedIndexGeneration`, which the token embeds, without any codemap path command, fence, or reschedule; the engine treats a stale token as terminal, and a completed job's coverage proof is rejected by `automaticSelectionCoverageProofIsCurrent`, so automatic planning returns `publicationStale` on every call with no restart path. Fix: a store-owned projection applied-index stamp that does not follow projection-neutral batches (`WorkspaceAppliedIndexBatchEvent.isCodemapProjectionNeutral`), consumed by the single token builder so every token consumer agrees; runtime-only, same wrap semantics. Reporting stays terminal; no automatic rearming from status queries; engine staleness semantics unchanged; S4 and the historical trigger stay out of scope. Proven first by a deterministic store-level reproduction (`PromptContextAccountingServiceTests+NeutralCatalogBatches`) that failed before the fix with the exact live signature.
- D9b (OracleD/E round 2, 2026-10-20): the deterministic probe showed a second parked class (a discoverable folder added or an empty folder removed with no file change bumps the catalog generation inside the path-local catalog mutation, where sessions are not detached, with no path command), so neutrality is "no file-level change" (`upsertedFiles`, `removedFileIDs`, `removedFilePaths`, `modifiedFileIDs`, `modifiedFileSourceSnapshotsByID` all empty, no full resync, no unload) and `topologyGeneration` also became a store-owned stamp set with the applied-index stamp on non-neutral batches. Both reviewers accepted the two-stamp design; adopted hardening: neutrality enforced by effect (DEBUG assertion that a neutral patch touches no file), guard tests that prove the batch landed (raw generations, neutral-batch count, folder record) and that the ordered projection file view is unchanged, a neutral-after-relevant check, and a payload-shape table for the predicate. Fence-and-relaunch for folder-only batches was rejected by both reviewers.
- D10 (2026-10-20): Step 4 live acceptance on the D9b build passed for quiet cold convergence, warm recounts, neutral (ignored-file) churn, and post-churn recovery; a tracked-file modification every 30 s still prevents completion because every `.modified` path command cancels and relaunches the full projection. Owner decision pending: accept that as known behavior under sustained churn, or reopen S4 / the Step 3b per-root cooldown. The D8 workers' zero-map state is closed.
- D11 (owner, 2026-10-20): accept that a tracked-file modification every 30 s prevents the projection from completing until the churn stops (full rerun per `.modified` path command, recovery under 90 s afterwards) as known behavior; do not reopen S4 incremental rerun or the Step 3b per-root cooldown within this plan. Plan closed; durable facts distilled into `docs/context/codemap-source-authority-recovery.md`.
