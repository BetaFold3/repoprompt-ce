# Claude MCP connection health, watchdog loss recovery, and helper crash guard

Scope: read when the task touches the MCP tool-execution watchdog's forced disconnect, run connection-loss events (`AgentMCPRunConnectionLoss`, `AgentMCPRunLaunchIdentity`), the helper-exit watch or helper process identity (`MCPHelperProcessLiveness`, `MCPHelperPeerProcessSnapshot`), Claude native RepoPrompt MCP health (`currentRepoPromptMCPHealth`, `awaitRepoPromptMCPConnectedEvidence`), turn-boundary MCP recovery in `ClaudeAgentModeCoordinator`, or `Task.sleep` use in the `repoprompt-mcp` helper.
Authority: Authoritative
Last-verified: 2026-10-26

## Failure this guards against

A tool that ignores cancellation past the bounded execution deadline (30 s plus 5 s cancellation grace, `MCPTimeoutPolicy`) settles as `cleanupUnresponsive`. The app then force-disconnects that helper connection (`abortConnectionForExecutionWatchdog`, reason `tool_execution_watchdog`), and the `repoprompt-mcp` helper exits on `terminatedByServer` by design. Claude Code keeps the dead MCP server and can keep reporting a stale `connected` status, so the session silently loses RepoPrompt tools. The same silent loss follows when the helper dies or loses its socket for any other reason (crash, SIGKILL, idle timeout, peer EOF) and never restores the run route. Cooperative tools settle as `executionTimedOut(settlement: .cancellation)` and never disconnect; the `history` tool's cancellation contract lives in [the history query tools spec](../spec/history-query-tools.md).

## Contract

- **Event shape**: `AgentMCPRunConnectionLoss.reason` is `tool_execution_watchdog`, `helper_exited`, or `route_not_restored`; `closeReason` is the connection's terminal close reason (`tool_execution_watchdog` for watchdog events); `toolName` is set only for watchdog events.
- **Event sources** (`MCPConnectionManager`): every source builds one immutable loss per addressed launch through one shared builder, synchronously and before any suspension, and delivers each to its observer in a detached task. Delivery never delays or gates containment.
  - **Watchdog**: when a watchdog abort commits the connection's terminal state, one event per registered launch of that run.
  - **Helper-exit watch**: opened synchronously at a connection's first terminal commit (`persistAcceptedSocketTerminalRecord`) only for a bootstrap helper with a run route whose run has loss observers, not a watchdog terminal, while the manager is running and the connection belongs to the current lifecycle generation, and only when the close reason is not `run_completed`, `run_cancelled`, `server_shutdown`, `connection_replaced`, or `tool_execution_watchdog`. The only production registration (`registerAndStartBootstrapConnection`, reached from the bootstrap `postAccept` commit) records the generation under the same current-lifecycle guard, so a routed, observed connection rejected by the generation check is unexpected and logs a warning instead of silently disabling the watch. Addressees are fixed at open: launches whose agent process instance (PID plus start time, read when the observer registered) is in the helper's admission ancestry snapshot. A launch whose identity was unreadable at registration, or whose PID now names a different process, gets no event (logged). A single 1 s poller (`Task.sleep(nanoseconds:)`, weak self) runs only while observations exist and uses a monotonic clock. `stop()` cancels it (and cancels again at its end if the manager is no longer running), and a tick from a stale lifecycle cancels every observation. Helper `exited` (gone, zombie, or PID reused) at ≥ 2 s after close emits `helper_exited`. While a live connection that matches the helper (same session token, or an admission ancestry containing an addressed agent instance) is accepted but not yet routed, that wait extends to the 20 s route deadline. `alive` or `unknown` at ≥ 20 s emits `route_not_restored`. Unknown liveness never counts as exited. The observation retires before delivery, so each watch emits at most once, and the deadline is final: a matching successor routed just after it still leaves the emitted `helper_exited` (or `route_not_restored`) in place.
  - **Successor cancels**: a new authoritative run route for the same run (hooked at every `runIDByConnectionID` assignment through `assignRunRoute`, and re-checked before emission) from a live, non-terminal connection with the same session token, or whose admission snapshot contains an addressed agent instance, cancels the watch. An unrouted accept or a different launch's helper does not. The routed successor check and the unrouted deadline extension share one candidate predicate (`isLiveMatchingHelperCandidate`) and differ only in the route condition.
  - **Same-token readmission routes during the handshake**: a helper readmitted after a transient drop reaches `applyPendingPolicyIfAvailable` from the bootstrap approval handler. A consumable pending policy routes it (`mapConnectionToRunIDForPendingPolicy`); otherwise the live-run-affinity fallback (`applyRoutingFallback` → `applyLiveRunAffinity` → `mapConnectionToRunID`, or `applyRunPolicyStateIfAvailable` when no window binding is possible) routes it through `assignRunRoute`. No production caller passes `persistWindowBinding: false`. The only unrouted outcome is a rejection (for example another launch's reserved policy), which correctly ends in `route_not_restored` or `helper_exited`. An `idle_timeout` close is watched like any other: when enabled, the helper exits and the watch reports `helper_exited`.
  - **Helper reconnect timing** (`RepoPromptMCPCore.runTransport`): after a retryable socket failure (`CLIProxyRuntimePolicy.shouldRetry`: for example server closed, reset, refused, or timeout; never after `terminatedByServer`, `approvalDenied`, or a host disconnect), and only while the bridge ledger proves no protocol-active work (otherwise the helper exits and the watch reports `helper_exited`), the helper sleeps and then reconnects with the same session token. It is not immediate: within 60 s of the helper's first failure every retry waits 0.5 s plus up to 0.1 s jitter, so a transient drop is readmitted and re-routed within about a second, far inside the 20 s route deadline. After 60 s the wait is `min(30, 2^max(0, attempt − 121))` s plus up to 20 % jitter, capped at 30 s: 1 s until the 121st attempt, then 2, 4, 8, 16 s (16–19.2 s at the 125th), and 30 s from the 126th. Residual: `attempt` and the first-failure time are never reset for the helper's lifetime, so once a helper is more than 60 s past its first failure and has accumulated about 125 failed attempts (roughly a 100 s continuous outage), a later transient drop waits 16–30 s and can miss the 20 s deadline, reporting `route_not_restored` although the helper reconnects; the next turn then recovers through a restart.
  - **Unregister**: removing an observer removes its token from every open watch; a watch with no addressees left is cancelled.
  - In-process MCP server restarts (`server_shutdown`) are a non-goal: they produce no event.
- **Process identity** (`MCPHelperProcessLiveness.swift`): an injectable `MCPProcessTableReading` (production: sysctl `KERN_PROC_PID`) classifies a helper `MCPHelperProcessIdentity` (PID plus start time) as `alive`, `exited`, or `unknown`. Where the bootstrap peer PID is set, the manager captures a per-connection `MCPHelperPeerProcessSnapshot`: the peer identity plus at most 15 nearest-first ancestors.
- **Launch identity**: observers register per run with an `AgentMCPRunLaunchIdentity` (a per-spawn token plus the PID registered as the run's expected agent). At registration the manager reads that agent's process identity (PID plus start time) through the same process-table reader. Ownership is proven only when the helper's ancestry contains that same process instance, so a PID reused before the replacement registered, or before the old connection closed, proves nothing. Helper-exit addressing requires the admission snapshot. The watchdog path uses the snapshot when it contains the agent PID, so a helper reparented before the abort still proves its owner; when the snapshot is missing or lacks the PID, it falls back to a live ancestry query. A live query used while an admission snapshot exists must still describe the snapshot's helper process instance (`live.peer == snapshot.peer`); a recycled helper PID proves nothing. When the agent identity was unreadable at registration, the watchdog falls back to the PID alone and helper-exit addresses nobody, so even a one-off unreadable read disables helper-exit for that launch (logged per watch). `provesOwnership(by:)` requires a matching token and either a proven matching agent PID or, for unproven watchdog events, a connection admitted after the launch registered. Helper-exit events are always proven. A token alone is never proof, so a late event from an old launch cannot mark a successor unhealthy.
- **Health** (`ClaudeNativeProcessSessionController`): `unknown → connected → unhealthy`, reset at every spawn and shutdown. Registration is limited to `toolContext == .agentRun` launches. A valid loss marks the launch unhealthy, emits one non-terminal `.error` item with reason-specific wording (the in-flight turn keeps running), and republishes runtime status with RepoPrompt shown as `disconnected` (not `failed`, which the runner treats as terminal). The wording describes the close in plain words: "the RepoPrompt MCP helper process exited", "RepoPrompt closed the idle connection", or "RepoPrompt disconnected it from the dashboard" (`repoPromptMCPAppSideCloseDescription`). The raw close code appears only in the `mcp.health.unhealthy` log payload. The spawn installs the stdout reader token and `repoPromptMCPLaunchToken` together in `installSpawnLaunchTokens` (one argument, adjacent assignments, the only spawn-time writer), so `stdout_retired` always compares like with like; the retirement comparison applies only when a retired token exists. Stale, duplicate (across reasons), other-run and already-unhealthy losses are ignored, as is a loss for a launch whose stdout already reached EOF (`stdout_retired`). The coordinator gates and recovery read only `isUnhealthy`, so they are reason-agnostic.
- **Gates**: on an unhealthy launch, the `startOrResume` fast path and `sendUserMessage` throw `repoPromptMCPRecoveryRequired` before writing anything; the coordinator treats it as proven-not-written.
- **Recovery** (`ClaudeAgentModeCoordinator`): only at a turn boundary. Session preparation treats unhealthy like a launch-settings change: retire the launch, restart resuming the same session ID with the same settings, then require fresh connected evidence before submitting the new turn. A steering dispatch with a turn in flight gets one recovery attempt (interrupt, then the same restart), and the user sees a notice that the running turn was stopped to reconnect RepoPrompt tools. Recovery status text is shown only while a dispatch is active and is cleared on every early return, so an idle tab never keeps a stale "Restarting…" status. No mid-turn reconnect, no helper reconnect, and the failed tool call and prior user turn are never replayed.
- **Connected-evidence probe**: a bounded probe that starts with Claude's `mcp_status` control request.
  - If the CLI rejects or times out that request, the probe falls back to the app's live run route.
  - A missing RepoPrompt entry, or `pending`, keeps polling until the deadline. Only `failed` or `needs-auth` end the probe early.
  - The probe captures the launch token at entry and re-checks it after every suspension. If the launch was replaced, it returns not-connected (`mcp.health.probeSuperseded`) without touching health, so stale evidence can never certify a successor.
  - The loss observer is registered before the expected agent PID.
- **Fail closed**: pending recovery carries a generation; after every await, confirmation revalidates run, attempt, generation, and that the run is still active before failing anything. If evidence never arrives, the new launch is retired and an error says nothing was sent. While recovery is pending, the fresh-conversation fallback is suppressed, so a failed resume fails the run instead of silently starting a new conversation. Pending recovery is in-memory only and is cleared on conversation reset, provider identity reset, and `stop()`; cancel keeps it.
- **Unchanged by design**: the watchdog abort writes no kill file and does not mark the session token killed; a replacement helper gets a fresh token and connection ID and is re-admitted through the new PID's ancestry. Codex registers no observer.
- **Known limitation: later turns on a long-lived Claude process.** Every turn installs a one-shot bootstrap routing policy (`MCPBootstrapLease`) and waits up to 10 s for a new helper connection. When Claude keeps its existing helper, none arrives, the wait ends `routed: false`, and `revokeClientConnectionPolicy` → `cleanupRunRoutingState(for:)` unmaps every connection of that run. A tool call can re-map the existing connection, but none is guaranteed. So from the second turn on, a helper that dies or is watchdog-aborted while unrouted opens no watch and gets no loss event, unless the watchdog's call-time run ID still names the run.
  - **Live check (2026-10-26, current Claude CLI):** after two turns and the 10 s window, both a helper SIGKILL and a forced watchdog abort with no run ID produced no loss notice. Each time, Claude respawned a new helper under the same Claude process when turn 3 needed it. Turn 3's routing lease routed that helper, and turn 3's tool call succeeded with no restart.
  - **Impact:** no silent loss was observed, but recovery there depends on Claude's own respawn.
  - **Possible follow-up:** keep a launch-scoped route for a helper whose ancestry proves the launch's agent instance, instead of clearing it on a turn's routing-wait timeout.
- **Known benign notice**: when Claude exits normally it closes its MCP servers first. If it then takes more than 2 s to exit, the helper-exit watch can report `helper_exited` before Claude's stdout EOF retires the launch, and the transcript shows one spurious disconnect notice. Recovery is unaffected: the launch is ending, and the next turn starts a fresh launch anyway.

## Helper crash guard

Swift 6.3.x can abort in `swift_task_dealloc` under the generic `Task.sleep(for:)` specialization in helper binaries (swiftlang/swift#86204). `RepoPromptMCPCore` uses `Task.sleep(nanoseconds:)` only, enforced by the SwiftLint rule `no_generic_task_sleep_in_mcp_helper`. `RepoPromptPlatform/Infrastructure/Process/ProcessRelaunchHelper.swift`, also linked into the helper for relaunch mode, still uses `Task.sleep(for:)` and is not covered by the rule.

## Validation

Focused suites: `MCPHelperExitRunConnectionLossTests` (watch rules, successors, the unrouted-successor deadline extension, production same-token readmission through `debugApplyPendingPolicy`, agent PID reuse, the unreadable-identity fallback, poller lifecycle including a stale-lifecycle tick, detached delivery, snapshot ownership, and the DEBUG diagnostics ops), `MCPHelperProcessLivenessTests` (a real child before and after SIGKILL), `MCPExecutionWatchdogRunConnectionLossTests`, `ClaudeNativeRepoPromptMCPHealthTests`, `AgentModeRunServiceLifecycleTests` (includes the coordinator recovery tests in `ClaudeAgentModeCoordinatorMCPRecoveryTests.swift`), `MCPToolExecutionWatchdogTests`, `MCPToolExecutionWatchdogIntegrationTests`, `PersistentMCPResponseDeliveryTests`; `make dev-core-test` for the helper. Unit tests redirect terminal records with the DEBUG `debugSetTerminalRecordsDirectoryOverride`, and in DEBUG test processes `MCPRoutingStateStore` uses a per-process temporary file, so they never write under Application Support. `testProductionBootstrapRegistrationRecordsTheGenerationAndOpensAWatch` admits through the production bootstrap `postAccept` commit (socketpair, no listener); `testGenerationGuardRejectionOfARoutedObservedConnectionIsRecorded` covers the logged rejection; the same-token readmission test also runs as a Claude variant that keeps the expected agent PID registered.

Live acceptance tooling (DEBUG builds only):

- `__repoprompt_debug_diagnostics` ops `force_execution_watchdog_abort` and `soft_disconnect_connection` each require `allow_destructive=true` and a `connection_id` other than the caller's. The `connections` op rows carry `run_id`, `helper_process_start`, and `helper_ancestor_pids` (nearest first; the first is the Claude PID).
- `Scripts/claude_mcp_recovery_live.py` runs against an already-running DEBUG app through `rpce-cli-debug`. Its scenarios are idle helper SIGKILL, mid-turn helper SIGKILL, forced watchdog abort, soft disconnect (reconnect, no loss), and baseline. It prints a PASS/FAIL table.
  - **Comparisons**: all UUIDs are compared in canonical lowercase form on both sides (the app reports uppercase).
  - **Kill guard** (`kill_refusal`): it kills only a helper whose start time matches the admission snapshot, whose executable path (`ps -o comm=`, never split on spaces) or kernel accounting name (`ps -o ucomm=`, MAXCOMLEN-truncated) is `repoprompt-mcp` / `repoprompt_ce_cli_debug` / `repoprompt_ce_cli`, and whose live ancestry contains the run's Claude PID with Claude-CLI-shaped arguments (`looks_like_claude_cli`: stream-json input and output plus either a `--resume`/`--session-id` conversation or an `--mcp-config` from the app's `MCP/LaunchConfigs/` directory; the app's first launch carries no conversation flag, only restarts add `--resume`). It never kills itself or one of its own ancestors. The start-time match is second-granular (`ps lstart` has no sub-second field; the app's `seconds.microseconds` is compared by its integer part). A residual check-then-kill PID-reuse race of a few milliseconds remains (macOS has no pidfd).
  - **Mid-turn**: the mid-turn scenario aborts before killing if turn 1 is not running, and reports `waiting_for_input` as a likely permission prompt.
  - **Real-app shapes**: the raw-JSON `agent_run start` reply has no `run_id`, so the script reads it from `poll`; a session keeps the same run ID across turns and a steer reply carries it. A run route can clear when a turn ends, so turn 2's helper is captured while turn 2 is running and tool calls are counted per connection. A first launch has no conversation ID on its command line, so the conversation is located read-only as the one recently modified Claude `*.jsonl` containing the scenario's unique turn-1 marker. The default model is `claudeCode:sonnet:medium` (`--model-id` must be a `list_agents` Claude model ID). When Claude runs through a wrapper with its own config directory, pass `--claude-projects-dir` at a parent of every possible `projects` directory.
  - **Success checks**: the turn-2 reply must appear in an assistant row of the turn-2 `get_log` slice (`transcript_slice` requires the page's `turn_offset` to equal the turn count before the steer; turns count oldest-first). `get_log` row text is raw and is never entity-decoded; only attribute values such as the tool name are. A RepoPrompt tool result with status `success` must appear there, and the turn-2 helper connection's tool-call count must increase across the steer. Turn 1's prompt must occur exactly once among user records of Claude's own `<projects>/**/<conversation-id>.jsonl`, read-only (`--claude-projects-dir`, default `$CLAUDE_CONFIG_DIR/projects` or `~/.claude/projects`).
  - **Self-test**: `python3 -I Scripts/claude_mcp_recovery_live_selftest.py` (stdlib only) covers its pure helpers, including `get_log` parsing against trimmed fixtures in `Scripts/Fixtures/claude_mcp_recovery_live/` that keep the real capture shape with placeholder text.

Live acceptance passed on 2026-10-26 against the Dev app (`debug-optimized-incremental` build of this change), a real Claude CLI and `claudeCode:sonnet:medium`, with all five scenarios run one at a time. Every check passed:

- **baseline**: same Claude process, turn-2 tool success, no loss.
- **soft-disconnect**: the same helper reconnected on a new connection and restored the route, with no loss notice and no Claude restart.
- **watchdog**: "did not stop after its deadline".
- **idle-kill** and **midturn-kill**: "the RepoPrompt MCP helper process exited". The mid-turn loss was non-terminal and turn 1 completed.

For each of watchdog, idle-kill and midturn-kill, a new Claude process resumed the same conversation (`--resume <id>`) on the next turn, the old one exited, a RepoPrompt tool succeeded, and turn 1's prompt occurred exactly once in Claude's transcript (not replayed). `route_not_restored` was not exercised live; it is covered by unit tests. Kills after the second turn are covered only by the manual probes under "Known limitation" above, not by a script scenario.
