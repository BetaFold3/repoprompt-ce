# Claude MCP connection health, watchdog loss recovery, and helper crash guard

Scope: read when the task touches the MCP tool-execution watchdog's forced disconnect, run connection-loss events (`AgentMCPRunConnectionLoss`, `AgentMCPRunLaunchIdentity`), the helper-exit watch or helper process identity (`MCPHelperProcessLiveness`, `MCPHelperPeerProcessSnapshot`), Claude native RepoPrompt MCP health (`currentRepoPromptMCPHealth`, `awaitRepoPromptMCPConnectedEvidence`), turn-boundary MCP recovery in `ClaudeAgentModeCoordinator`, or `Task.sleep` use in the `repoprompt-mcp` helper.
Authority: Authoritative
Last-verified: 2026-10-27

## Failure this guards against

A tool that ignores cancellation past the bounded execution deadline (30 s plus 5 s cancellation grace, `MCPTimeoutPolicy`) settles as `cleanupUnresponsive`. The app then force-disconnects that helper connection (`abortConnectionForExecutionWatchdog`, reason `tool_execution_watchdog`), and the `repoprompt-mcp` helper exits on `terminatedByServer` by design. Claude Code keeps the dead MCP server and can keep reporting a stale `connected` status, so the session silently loses RepoPrompt tools. The same silent loss follows when the helper dies or loses its socket for any other reason (crash, SIGKILL, idle timeout, peer EOF) and never restores the run route. Cooperative tools settle as `executionTimedOut(settlement: .cancellation)` and never disconnect; the `history` tool's cancellation contract lives in [the history query tools spec](../spec/history-query-tools.md).

## Contract

- **Event shape**: `AgentMCPRunConnectionLoss.reason` is `tool_execution_watchdog`, `helper_exited`, or `route_not_restored`; `closeReason` is the connection's terminal close reason (`tool_execution_watchdog` for watchdog events); `toolName` is set only for watchdog events.
- **Event sources** (`MCPConnectionManager`): every source builds one immutable loss per addressed launch through one shared builder, synchronously and before any suspension, and delivers each to its observer in a detached task. Delivery never delays or gates containment.
  - **Watchdog**: when a watchdog abort commits the connection's terminal state, one event per registered launch of that run.
  - **Helper-exit watch**: opened synchronously at a connection's first terminal commit (`persistAcceptedSocketTerminalRecord`) only for a bootstrap helper with a run route whose run has loss observers, not a watchdog terminal, while the manager is running and the connection belongs to the current lifecycle generation, and only when the close reason is not `run_completed`, `run_cancelled`, `server_shutdown`, `connection_replaced`, or `tool_execution_watchdog`. The only production registration (`registerAndStartBootstrapConnection`, reached from the bootstrap `postAccept` commit) records the generation under the same current-lifecycle guard, so a routed, observed connection rejected by the generation check is unexpected and logs a warning instead of silently disabling the watch. Addressees are fixed at open: launches whose agent process instance (PID plus start time, read when the observer registered) is in the helper's admission ancestry snapshot. A launch whose identity was unreadable at registration, or whose PID now names a different process, gets no event (logged). A single 1 s poller (`Task.sleep(nanoseconds:)`, weak self) runs only while observations exist and uses a monotonic clock. `stop()` cancels it (and cancels again at its end if the manager is no longer running), and a tick from a stale lifecycle cancels every observation. Helper `exited` (gone, zombie, or PID reused) at ≥ 2 s after close emits `helper_exited`. While a live connection that matches the helper (same session token, or an admission ancestry containing an addressed agent instance) is accepted but not yet routed, that wait extends to the 20 s route deadline. `alive` or `unknown` at ≥ 20 s emits `route_not_restored`. Unknown liveness never counts as exited. The observation retires before delivery, so each watch emits at most once, and the deadline is final: a matching successor routed just after it still leaves the emitted `helper_exited` (or `route_not_restored`) in place.
  - **Successor cancels**: a new authoritative run route for the same run (hooked at every `runIDByConnectionID` assignment through `assignRunRoute`, and re-checked before emission) from a live, non-terminal connection with the same session token, or whose admission snapshot contains an addressed agent instance, cancels the watch. An unrouted accept or a different launch's helper does not. The routed successor check and the unrouted deadline extension share one candidate predicate (`isLiveMatchingHelperCandidate`) and differ only in the route condition.
  - **Same-token readmission routes during the handshake**: a helper readmitted after a transient drop reaches `applyPendingPolicyIfAvailable` from the bootstrap approval handler. A consumable pending policy routes it (`mapConnectionToRunIDForPendingPolicy`); otherwise the live-run-affinity fallback (`applyRoutingFallback` → `applyLiveRunAffinity` → `mapConnectionToRunID`, or `applyRunPolicyStateIfAvailable` when no window binding is possible) routes it through `assignRunRoute`. No production caller of `mapConnectionToRunID` passes `persistWindowBinding: false` (only the retained-helper refresh does, to `applyRunPolicyStateIfAvailable`). The only unrouted outcome is a rejection (for example another launch's reserved policy), which correctly ends in `route_not_restored` or `helper_exited`. An `idle_timeout` close is watched like any other: when enabled, the helper exits and the watch reports `helper_exited`.
  - **Helper reconnect timing** (`RepoPromptMCPCore.runTransport`): after a retryable socket failure (`CLIProxyRuntimePolicy.shouldRetry`: for example server closed, reset, refused, or timeout; never after `terminatedByServer`, `approvalDenied`, or a host disconnect), and only while the bridge ledger proves no protocol-active work (otherwise the helper exits and the watch reports `helper_exited`), the helper sleeps and then reconnects with the same session token. It is not immediate: within 60 s of the helper's first failure every retry waits 0.5 s plus up to 0.1 s jitter, so a transient drop is readmitted and re-routed within about a second, far inside the 20 s route deadline. After 60 s the wait is `min(30, 2^max(0, attempt − 121))` s plus up to 20 % jitter, capped at 30 s: 1 s until the 121st attempt, then 2, 4, 8, 16 s (16–19.2 s at the 125th), and 30 s from the 126th. Residual: `attempt` and the first-failure time are never reset for the helper's lifetime, so once a helper is more than 60 s past its first failure and has accumulated about 125 failed attempts (roughly a 100 s continuous outage), a later transient drop waits 16–30 s and can miss the 20 s deadline, reporting `route_not_restored` although the helper reconnects; the next turn then recovers through a restart.
  - **Unregister**: removing an observer removes its token from every open watch; a watch with no addressees left is cancelled.
  - In-process MCP server restarts (`server_shutdown`) are a non-goal: they produce no event.
- **Process identity** (`MCPHelperProcessLiveness.swift`): an injectable `MCPProcessTableReading` (production: sysctl `KERN_PROC_PID`) classifies a helper `MCPHelperProcessIdentity` (PID plus start time) as `alive`, `exited`, or `unknown`. Where the bootstrap peer PID is set, the manager captures a per-connection `MCPHelperPeerProcessSnapshot`: the peer identity plus at most 15 nearest-first ancestors.
- **Launch identity**: observers register per run with an `AgentMCPRunLaunchIdentity` (a per-spawn token plus the PID registered as the run's expected agent). At registration the manager reads that agent's process identity (PID plus start time) through the same process-table reader. Ownership is proven only when the helper's ancestry contains that same process instance, so a PID reused before the replacement registered, or before the old connection closed, proves nothing. Helper-exit addressing requires the admission snapshot. The watchdog path uses the snapshot when it contains the agent PID, so a helper reparented before the abort still proves its owner; when the snapshot is missing or lacks the PID, it falls back to a live ancestry query. A live query used while an admission snapshot exists must still describe the snapshot's helper process instance (`live.peer == snapshot.peer`); a recycled helper PID proves nothing. When the agent identity was unreadable at registration, the watchdog falls back to the PID alone and helper-exit addresses nobody, so even a one-off unreadable read disables helper-exit for that launch (logged per watch). `provesOwnership(by:)` requires a matching token and either a proven matching agent PID or, for unproven watchdog events, a connection admitted after the launch registered. Helper-exit events are always proven. A token alone is never proof, so a late event from an old launch cannot mark a successor unhealthy.
- **Health** (`ClaudeNativeProcessSessionController`): `unknown → connected → unhealthy`, reset at every spawn and shutdown. Registration is limited to `toolContext == .agentRun` launches. A valid loss marks the launch unhealthy, emits one non-terminal `.error` item with reason-specific wording (the in-flight turn keeps running), and republishes runtime status with RepoPrompt shown as `disconnected` (not `failed`, which the runner treats as terminal). The wording describes the close in plain words: "the RepoPrompt MCP helper process exited", "RepoPrompt closed the idle connection", or "RepoPrompt disconnected it from the dashboard" (`repoPromptMCPAppSideCloseDescription`). The raw close code appears only in the `mcp.health.unhealthy` log payload. The spawn installs the stdout reader token and `repoPromptMCPLaunchToken` together in `installSpawnLaunchTokens` (one argument, adjacent assignments, the only spawn-time writer), so `stdout_retired` always compares like with like; the retirement comparison applies only when a retired token exists. Stale, duplicate (across reasons), other-run and already-unhealthy losses are ignored, as is a loss for a launch whose stdout already reached EOF (`stdout_retired`). The coordinator gates and recovery read only `isUnhealthy`, so they are reason-agnostic.
- **Gates**: on an unhealthy launch, the `startOrResume` fast path and `sendUserMessage` throw `repoPromptMCPRecoveryRequired` before writing anything; the coordinator treats it as proven-not-written.
- **Recovery** (`ClaudeAgentModeCoordinator`): only at a turn boundary. Session preparation treats unhealthy like a launch-settings change: retire the launch, restart resuming the same session ID with the same settings, then require fresh connected evidence before submitting the new turn. A steering dispatch with a turn in flight gets one recovery attempt (interrupt, then the same restart), and the user sees a notice that the running turn was stopped to reconnect RepoPrompt tools. Recovery status text is shown only while a dispatch is active and is cleared on every early return, so an idle tab never keeps a stale "Restarting…" status. No mid-turn reconnect, no helper reconnect, and the failed tool call and prior user turn are never replayed.
- **Connected-evidence probe**: a bounded probe that starts with Claude's `mcp_status` control request.
  - If the CLI rejects or times out that request, the probe falls back to the app's live run route.
  - A missing RepoPrompt entry, or `pending`, keeps polling until the deadline. Only `failed` or `needs-auth` end the probe early.
  - The probe captures the launch token at entry and re-checks it after every suspension. If the launch was replaced, it returns not-connected (`mcp.health.probeSuperseded`) without touching health, so stale evidence can never certify a successor.
  - The loss observer is registered before the expected agent PID.
- **Fail closed**: pending recovery carries a generation; after every await, confirmation revalidates run, attempt, generation, and that the run is still active before failing anything. If evidence never arrives, the new launch is retired and an error says nothing was sent. While recovery is pending, the fresh-conversation fallback is suppressed, so a failed resume fails the run instead of silently starting a new conversation. Pending recovery is in-memory only and is cleared on conversation reset, provider identity reset, and `stop()`; cancel keeps it.
- **Unchanged by design**: the watchdog abort writes no kill file and does not mark the session token killed; a replacement helper gets a fresh token and connection ID and is re-admitted through the new PID's ancestry. Codex registers no observer.
- **Later-turn route retention** (`MCPConnectionManager`, `MCPBootstrapLease`): every turn installs a one-shot bootstrap routing policy and normally waits up to 10 s for a new helper. When Claude keeps its helper, none arrives, so the lease either releases early (7) or revokes its policy (5). `defaultPolicyClearer` is the only production caller of `revokeClientConnectionPolicy`. The effect: a helper that dies or is watchdog-aborted after a later turn still has its run route, so the helper-exit watch opens and the watchdog loss needs no call-time run ID. Invariants:
  1. **Scope:** Claude native clients only (`retainsProvenRunRoutes`, canonical family `claude-code`; checked in `connectionHoldsProvenRunRoute`, the turn-start refresh, the early release and the hooks). Other clients never hold a proven route: every revoke does a full `cleanupRunRoutingState`, there is no refresh, and the early release always refuses.
  2. **Ownership rule** (`connectionHoldsProvenRunRoute`; fails closed, no live re-capture). A route is proven only when all of these hold:
     - The connection is routed to the run, live and non-terminal (`isLiveNonTerminalConnection`), and admitted for the client.
     - It is bound to the run policy's window: `connectionWindowMap[id] == runPolicyStateByRunID[runID]?.windowID`. No run policy state, or a missing or different binding, proves nothing.
     - `ancestryProvesAgentInstance` holds for some expected PID of the run (exactly that one PID for launch-bound evidence): the PID's registered instance is in the helper's ADMISSION snapshot (same PID and start time) and is still alive.

     The registered instance (`registeredAgentIdentity`) is the one read at expected-PID registration. Otherwise it is the single instance that every readable loss observer of that PID agrees on. Observers that disagree register none: expected-PID registration carries no launch token, so the manager has no current launch to prefer.

     These prove nothing: no snapshot; a snapshot without the PID; an agent unreadable at both registrations; a PID reused between registration and admission; an exited or zombie agent. During a restart overlap, both launches' helpers are owned. Once the old PID clears, only the new one is.
  3. **Restore paths bind the policy window.** Every route restore ends in `applyRunPolicyStateIfAvailable(persistWindowBinding: true)`, which sets `connectionWindowMap` to the run policy's window. The restore paths are:
     - the same-token reconnect (`applyRoutingFallback` → `applyLiveRunAffinity` → `mapConnectionToRunID`, or `applyRunPolicyStateIfAvailable` directly when the mapping is refused);
     - the tool-call affinity restore (PRIORITY 2b);
     - persisted-policy hydration.

     `preferredLiveRunAffinity` also returns the policy's window, and the pending-policy apply writes `policy.windowID`, so retention survives a soft disconnect. Each affinity restore that leaves the connection routed to the run records DEBUG `live_affinity_route_restored` (`path`: `routing_fallback:<reason>`, `persisted_policy_hydration:<reason>` or `tool_call`), a route assignment like `policy_applied`. The `runIDForConnection` window-scan fallback re-assigns only an actor route, which proves nothing unless its binding already matches.
  4. **Hooks** (`unrouteDependentsOfReleasedAgentIdentities`):
     - **Trigger:** runs synchronously at the end of every change that can release a registered instance, with `registeredAgentIdentities` sampled at its start. The changes are:
       - `removeExpectedAgentPID` (every `clearExpectedAgentPID`);
       - a re-registration (`registerExpectedAgentPID`);
       - a loss-observer registration (a disagreeing observer releases the fallback instance);
       - a loss-observer unregistration.
     - **Dependents:** the run's routed Claude connections whose admission snapshot contains a released instance. They are found from registration and ancestry, never from liveness, so a helper whose agent already exited is found too.
     - **Unroute:** each dependent that fails the full proof is unrouted actor-side in the same step (`unrouteRunConnections`): its route, its fingerprint, and its session's affinity unless a still-routed connection shares it. `routingSessionKey(for:)` is the one derivation of the affinity key.
     - **Window cleanup:** scheduled through `cleanUpPrunedRunWindowMappings`. DEBUG `proof_lost_routes_unrouted` carries `cause`, `unrouted_connection_count` and `window_mapping_removed`.
     - **Left alone:** proven dependents, and routes not descended from a released instance. The hook never calls `cleanupRunRoutingState`, because a restart's new turn still needs its seeded run state and queue entry.
  5. **Revoke:** always clears the pending policy, its application ID and the client policy. Its routing half then runs four steps:
     1. One prune: `pruneUnprovenRunRoutes` unroutes every unowned connection synchronously.
     2. One window-side hop, only for mappings still pointing at a pruned connection.
     3. The backstop refresh.
     4. One synchronous final check (`finishRetainedRunRouting`).

     If any live proven route remains, the run keeps its routes, run policy, run window, admission, affinity and window mapping. If none remains, `cleanupRunRoutingState` runs; it is the only full cleanup, and it drops each connection's fingerprint just as an unroute does. Retention never re-points or re-registers a window mapping.
     - DEBUG `policy_revoked` and `routing_cleanup_if_unproven` carry `routing_preserved`, `preserved_connection_count`, `pruned_connection_count` and `window_mapping_removed`.
     - `cleanupRunRoutingIfUnproven` (on `AgentMCPHosting`) is the same routing half, without any policy.
     - `releaseWhenRouted` revokes after a failed wait only if neither cancellation cleanup nor the early release already did.
  6. **Refresh:**
     - **Fingerprint:** each connection records the projection last applied (`AppliedRunPolicyProjection`: restricted and additional tools, allowed-tools override, session profile, purpose, task label kind, `allowsAgentExternalControlTools`). The pending-policy apply records it only when it equals the run state's. It is dropped on removal, on every unroute, by `cleanupRunRoutingState`, and on pending-policy restore. A missing fingerprint counts as different.
     - **What gets refreshed:** only proven connections whose fingerprint differs, with one `tools/list_changed` each. A window-binding difference alone never triggers a refresh. After a suspension, the refresh stops once the run's projection has changed, and it re-proves each connection right before its apply.
     - **What it writes:** the policy only (`persistWindowBinding: false`, `bindsRunTab: false`). It never assigns a route or rebinds a window or the run tab, so it never moves the window's run mapping or schedules the replacement of the connection holding it. A retained helper's run-tab binding is refreshed only by its own tool calls (the holder's fast path or the per-call rebind, 10).
     - **Turn start:** the lease calls `refreshRetainedRunPolicyForTurnStart` right after `releaseOwnedGate(reason: "expected_pid_policy_armed")`, outside `HeadlessAgentConnectionGate`. `acquire()` checks cancellation after that gate release and again after the refresh.
  7. **Early release:**
     - **Entry:** after `sendClaudeNativeMessage`, the runner passes `repoPromptMCPLaunchAgentPID` to `releaseWithProvenExistingRoute(agentPID:)`, guarded by `released, !hasReleased, !cleanupRequested`. A nil PID or a refusal falls back to `releaseWhenRouted`.
     - **The PID:** the spawned process's PID, installed with the current launch token. It may not be registered yet, and the manager fails closed until it is. Both launch paths register the same `spawned.pid`; a DEBUG log reports a mismatch.
     - **The release** (`releasePendingRunPolicyForProvenRoute`) runs in order:
       1. Requires launch-bound evidence for that PID (`hasAuthoritativeLiveRunRoute(…requiredAgentPID:)`: the mapped connection must also be live, non-terminal and owned by exactly that PID's instance).
       2. Refuses while an application of the run's policy is in flight or reserved.
       3. Removes the turn's queue entry, synchronously with those checks.
       4. Refreshes every proven connection.
       5. Re-checks the route and the projection fence.

       A `false` leaves the turn to the routing wait, whose revoke finds no queue entry and keeps the proven routes.
     - **After a release:** the lease never revokes. Failure and cancellation cleanups call `cleanupRunRoutingIfUnproven` once.
     - **Connected evidence:** Claude's connected-evidence fallback passes `currentLaunchAgentPID`; OMP passes nil.
     - **DEBUG events:** `policy_released_for_proven_route` and `route_wait_skipped_proven_route`.
     - **Why it exists:** it removes the up-to-10 s delay before a later turn's events render.
  8. **Restriction APIs** (`setRestrictedTools`, `addRestrictedTools`, `clearRestrictedTools`; these predate this work and have no production caller): on a connection routed to a run or carrying a run-policy fingerprint, the run policy alone owns the restricted set, so these do nothing and write a DEBUG log. Otherwise they keep their original replace, add and remove behaviour.
  9. **Expected-agent identities** never outlive the run's expected-PID set. `cleanupRunRoutingState` keeps expected PIDs and their identities.
  10. **Window-route holder:** owning the helper process (2) never grants the window's run mapping. That mapping (`connectionIDByRunID`) has one holder, and binding the run tab for another connection replaces it (`registerRunIDMapping` schedules `handleConnectionReplaced`: a soft disconnect for the same session token, otherwise a hard termination).
      - **Displacing (authorized) paths:** admission, pending-policy application, handover and the defaults of `ensureTabBoundForRunIfPossible` / `applyRunPolicyStateIfAvailable` / `mapConnectionToRunID`. Only these reclaim the slot from another holder, so a fresh helper still replaces the old one.
      - **Request-originated paths never replace a different holder:** the per-tool-call rebind (`runScopedTabRebindFallbackForToolCall`), the request rehydrate (`rehydrateRunTabContextForConnectionIfPossible(displacesHolder: false)`, from the `agent_run`/`agent_explore` spawn parent, the `agent_run` launch source and `ask_user`), and `mapConnectionToRunIDWithOutcome(displacesHolder: false)` from the tool-call live-affinity restore (PRIORITY 2b, source `tool_call_affinity_restore`) and persisted-policy hydration (source `persisted_policy_hydration`). The decision is made inside the MainActor step that would bind or register: if `connectionIDByRunID[runID]` is nil or the caller, it proceeds; if it is any other connection, it yields. Nothing sampled earlier authorizes a replacement: there is no liveness, routing, route-history or launch-recency evidence (the earlier recency guard, its route history and the admission ordinal are removed).
      - **The whole operation is non-displacing:** `mapConnectionToRunIDWithOutcome`'s success branch passes the intent to `applyRunPolicyStateIfAvailable(tabRebindDisplacesHolder:)`. A holder admitted after the caller's registration (during a suspension) is therefore never displaced, and the operation reports `.yieldedToHolder` instead of `.mapped`. The rest of a tools/call is audited too: the legacy `_tabID` bind carries no run ID and touches only the caller's own binding, while resolver handover (step 2) and pending run-scoped intent (step 4) are authorized intents and stay displacing.
      - **Family scope:** the yield is gated by `requestPathYieldsToDifferentHolder`, which is `isClaudeNativeClient` (canonical family `claude-code`, the same helper `retainsProvenRunRoutes` and the removal sweep use). Codex, ACP/OMP and headless callers keep the displacing request paths of HEAD.
      - **What a yield leaves:** a `.yieldedToHolder` outcome (`RunTabRebindOutcome`, `RunTabRehydrateOutcome`, `RunMappingOutcome`). The caller is routed to the run actor-side with the run policy applied and no run-tab bind, so it is never policy-less. `live_affinity_route_restored` is recorded only for a successful mapping. A yield does not signal the routing waiter: the run's window mapping did not change (its holder signalled when it registered), and the caller holds none. The DEBUG events are `tab_rebind_yielded_to_holder` (bind) and `run_mapping_yielded_to_holder` (mapping, which also carries `route_assigned` and `policy_applied`). Both carry `source`, `holder_connection_id`, `reason=different_holder` and `window_id`.
      - **Empty-slot fill:** when a request-originated bind or mapping (`displacesHolder: false`) takes the run's empty window-mapping slot, it records DEBUG `run_tab_rebound_empty_slot` (`source`, `mechanism` `run_tab_bind` or `run_mapping`, `window_id`). That is a route assignment re-creating the mapping, for example after a prune or a holder's removal cleanup. A mapping's own policy run-tab bind does not record it again, and neither a yield nor the holder's own tab repair records it.
      - **Dead holders vanish so request paths can repair:** existing cleanups are window close, `cleanupRunRoutingState`, the prune and proof-loss unroute (`cleanUpPrunedRunWindowMappings`), the pending-policy rollback, and a removed connection's tab-context teardown (which clears a mapping only when the bound context carries the run). New: `removeConnection` of a Claude native, non-`.discoverRun` connection runs `releaseRemovedConnectionRunWindowMappings`. In every window it visits the connection's routed run, its reverse mapping and every run it holds, and clears each through the receipt-checked `cleanupRunIDMapping`, which removes only an entry still pointing at that connection. Until that cleanup runs, a dead, terminal or unrouted holder still holds the slot, and callers yield and resolve through step 4b.
      - **Resolver rule (step 4b of `resolveTabContext`):** a connection whose actor-side run route has a policy naming a tab (`RequestMetadata.actorRoutedRunTab`, from `actorRoutedRunPolicyTab`), and that has no run-tab binding of its own, resolves to that run tab: source `.actorRunRoute`, `explicitlyBound: false`, no active UI capture. It never falls through to active-tab compatibility, and it fails closed when the tab is in another window. It is client-agnostic, a fail-closed rule for any routed connection with a run tab (only Claude native request paths yield the mapping). Every tab-context tool goes through it: `captureRequestMetadata`, `contextForCurrentRequest` and the `context_builder` resolve read the run tab in the same actor hop as `runPurpose` (`requestRoutingContext`), and the spawn parent and `agent_run` launch source re-read it after their rehydrate. `RequestMetadata(actorRoutedRunTab:)` and `resolveTabContext(actorRoutedRunTab:)` have no default, so every call site states it. `ask_user` treats the controller as `.unverified`, as before.
      - **Step 1 behaviour change:** `requiredRunID` is `connectionIDToRunID[connection] ?? actorRoutedRunTab?.runID`. An actor-routed connection bound to a non-run tab now has that binding released (keeping its run hint) and resolves the run tab through step 4b. At HEAD this happened only when the window's reverse mapping existed.
      - **Connected evidence:** `hasAuthoritativeLiveRunRoute` and the early release need the window mapping. Consider a new-launch helper whose admission bind failed while the old holder was still live: it yields until the old holder's removal cleanup. Until then a later turn takes the routing wait (`routing_preserved=true`), and an old CLI that relies on the app-route fallback of the connected probe can fail its recovery probe. The gap is transient, ending once the old holder is removed and the new helper makes a request. The probe itself makes no request, so the yield does not change it compared with HEAD. `route_not_restored` is unaffected, because helper-exit successors qualify by actor route, which a yield keeps.
  - **Accepted and open:**
    - **Conservative fallback:** once a prune or a proof loss removes the run's window mapping, launch-bound evidence fails, and turns take the routing wait (whose revoke still keeps the proven route). This lasts until an eligible request or an authorized routing operation restores the mapping. The eligible request is the kept helper's next tools/call: its per-call run-tab rebind into the empty slot, which fires for any routed connection without a `_tabID` argument and with a resolved window, whether or not it holds a tab binding, except `read_file` / `file_search` under an Agent Mode run (`MCPConnectionManager.swift` `shouldAttemptRunScopedTabRebindFallback`, `shouldSkipPerCallRunScopedTabRebindFallback`). It records `run_tab_rebound_empty_slot`. The authorized operations are admission, pending-policy application and handover. A tab-less run route (no `tabID` in the run policy) cannot use run-tab repair (`ensureTabBoundForRunIfPossible` returns `.noRunTab`) and may stay on the wait fallback.
    - A cleanup hop can remove a mapping that was re-created during the hop. The turn falls back to the wait.
    - When proof is lost without an event (the agent exits while its PID is still registered), nothing happens until the next prune or that PID's clear.
    - **Respawn race:** a narrow window that fails safe with `route_not_restored`.
    - **Open:** stale-lease fencing is unchanged. A stale lease's pending policy is not fenced against a newer turn's lease.
    - **Same-controller respawn:** after an unexpected stdout EOF the controller keeps its old expected PID registered (`handleStdoutEOF` never clears it). `registerExpectedAgentPIDIfNeeded` now clears that previous PID (`clearExpectedAgentPID`, which releases its dependents) before registering the new one. That closes the window in which a reused stale PID passed the PID-only admission gates (`isExpectedAgentDescendant` / `isAncestor`). Every coordinator replacement awaits the old controller's `shutdown()` (which clears its PID) before the successor starts.
      - **Route proof is not exposed to PID reuse:** `registerExpectedAgentPID` records the instance (PID and start time) at registration, and `ancestryProvesAgentInstance` requires the helper's admission snapshot to contain exactly that instance and `classify` to find it alive. A different start time is `.exited`, so a reused PID proves nothing.
    - **Window-route holder residuals:**
      - A dead, terminal or unrouted holder keeps the slot until its cleanup runs; meanwhile request paths yield and resolve through step 4b.
      - The rare admission-bind failure above leaves a transient evidence gap. A possible follow-up, not implemented: when the removal sweep empties a run's slot, schedule a non-displacing bind for that run's live proven-route connection. It would fill only an empty slot.
      - The removal sweep is scoped to Claude native, non-`.discoverRun` connections. Other families keep the tab-context teardown of HEAD.
      - A yielded mapping's route assignment records no `live_affinity_route_restored` event.
      - `.actorRunRoute` snapshots start no tab mirroring.
      - **Re-route to another run (latent):** a re-route that registers the new run in the same window drops the previous run's forward entry (`registerRunIDMapping`, and receipt-checked in `registerPendingPolicyRunIDMapping`). The other re-routes clear nothing there: a yielded request mapping, a policy without a run tab, or a registration in another window. So a Claude native connection re-routed actor-side to another run can leave its forward mapping of the previous run behind. Until that connection is removed, request paths for the previous run yield to it and resolve through step 4b, and later turns of that run take the routing wait. This is safe (never policy-less, never the active tab) and transient: the removal sweep visits every run a window maps to the connection and clears the entry. A release before the re-route is not implemented, because it would need a hop and a generation fence against mappings installed during that hop.
        - **Reachability:** no normal production path re-routes an admitted Claude connection to a different run. A pending policy is consumed only during the MCP initialize handshake (`MCPConnectionManager.swift` `applyPendingPolicyIfAvailable`, called at admission before `notifyConnectionWaiters`). A PID-gated policy also needs the helper to descend from that run's expected agent (`canConsumePendingPolicy` → `isExpectedAgentDescendant`). The admission routing fallback (`applyRoutingFallback`: session-token live affinity, expected-PID affinity) is called only from `applyPendingPolicyIfAvailable`. The session token is per helper process (`RepoPromptMCPCore.swift`: "Stable session token for this CLI process instance", `UUID().uuidString`), and every Claude launch writes its own `--mcp-config` (`ClaudeNativeProcessSessionController.swift` `prepareLaunchConfig`). After admission, the route writers keep the connection's own run: 2b `restoreRunAffinityForToolCall` runs only for a connection with no window mapping, keyed by its own session's live affinity; the rehydrate and the per-call rebind use `runIDForConnection`; the refresh passes `persistWindowBinding: false`; and the pending rollback restores the prior route. So an admitted connection's actor route is rewritten only to the same run, or cleared. A different-run re-route takes a test seam (`debugApplyRunPolicyState`) or a change of the session's live affinity to another run while the connection holds no window mapping.
- **Known benign notice**: when Claude exits normally it closes its MCP servers first. If it then takes more than 2 s to exit, the helper-exit watch can report `helper_exited` before Claude's stdout EOF retires the launch, and the transcript shows one spurious disconnect notice. Recovery is unaffected: the launch is ending, and the next turn starts a fresh launch anyway.

## Helper crash guard

Swift 6.3.x can abort in `swift_task_dealloc` under the generic `Task.sleep(for:)` specialization in helper binaries (swiftlang/swift#86204). `RepoPromptMCPCore` uses `Task.sleep(nanoseconds:)` only, enforced by the SwiftLint rule `no_generic_task_sleep_in_mcp_helper`. `RepoPromptPlatform/Infrastructure/Process/ProcessRelaunchHelper.swift`, also linked into the helper for relaunch mode, still uses `Task.sleep(for:)` and is not covered by the rule.
