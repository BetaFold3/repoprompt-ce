Technical implementation report · 8 August 2026

Build and test feedback, made dramatically faster

RepoPrompt CE now has a measured parallel test path, a stable SwiftPM build environment, and an evidence-gated fast packaging option. On the profiled Mac Studio, the full local root test feedback loop fell from about 13m18s to a 2m46s median, while a warm no-change debug build fell from about 24s to about 9.9s by default.

Executive summary

The biggest win came from using the machine’s cores safely

The original full test run spent roughly 96% of its time executing tests in one process. The parallel runner builds the tests once, then distributes whole test suites across eight direct xctest workers. Whole suites stay together, suites with known shared state are serialized, and the coordinator verifies that every expected test ran exactly once.

Implementation explained simply

Six changes work together

1 · Build onceRecord a valid test bundleThe conductor fingerprints source, environment, and toolchain.
2 · DiscoverCreate the test censusThe runner knows exactly which suites and methods must execute.
3 · DistributeEight workers pull suitesLongest suites start first; unsafe suites use dedicated lanes.
4 · ProveAggregate and check parityMissing, duplicated, crashed, timed-out, or failed suites fail the job.

1. Canonical SwiftPM environment

Scripts/canonical_swift.sh launches every coordinated and packaging Swift command with the same minimal allowlisted environment. SwiftPM includes the child environment in its cache key; volatile per-job values had been turning genuine no-op work into 14–27 second replans.

Observed in code Conductor and packaging Swift calls now use the wrapper.

2. Parallel suite runner

Scripts/parallel_xctest_runner.py uses a longest-processing-time queue, per-worker temporary directories, serial tags, an exclusive lane, ledger-derived deadlines, process-group cleanup, one diagnostic retry, JSON summaries, and strict test-count parity.

Observed in tests 10/10 full runs passed with 502 suites and 4,983 tests each.

3. Conductor integration

make dev-test-parallel is now the promoted source-validating root lane. It invalidates any old ticket, snapshots source, builds the tests, fingerprints the artifact, runs the worker pool, and fails closed if source, environment, toolchain, artifact path, or artifact fingerprint drifts. It holds both machine-wide heavy and XCTest slots so builds and worker pools cannot compete.

Observed in code WORKERS and FILTER are supported.

4. Codemap race correction

The Git capability capture previously treated size and timestamp changes on every ancestor directory up to the filesystem root as authority changes. Parallel tests creating unrelated sibling files under the shared temp parent could therefore abort a stable capture. Intermediate directories now require stable descriptor identity; the leaf still receives the full fail-closed stat check.

Observed in tests New deterministic churn coverage preserves leaf replacement and symlink-swap rejection.

5. Evidence-gated fast packaging

make dev-build FAST=1 fingerprints the app binaries, helpers, framework, Info.plist, signing identity/mode, and packaging script. Only an exact match to the last fully verified package can skip deep signature verification, redundant post-sign architecture validation, and the embedded-helper smoke.

Observed in code Signing, identity checks, layout checks, and pre-sign architecture checks still run.

Test timeout correction

One routing test invoked a non-detached stub that never produced the state awaited by the default 120-second timeout. Supplying a one-second timeout preserves the path under test while removing the accidental two-minute stall.

Observed in tests The method fell from 121.3s to 1.31s; its 57-test suite passed.

Major turns and decisions

The final design came from measured failures, not assumptions

  1. Naive SwiftPM parallelism was rejected. swift test --parallel finished faster but broke 70 tests at method granularity. Multiple swift test --skip-build processes against one .build directory serialized on SwiftPM’s lock and took about as long as serial execution.
  2. The original 2–3 minute prediction was corrected. The first 12-worker direct-xctest experiment took 239s but had 74 failures. The Oracle review required reporting that as a proof of opportunity, not a successful result, and asked for a worker sweep plus 10 consecutive greens.
  3. APFS clone-shards failed the relocation gate. After hiding the seed build directory, an absolute path to the Sentry artifact still pointed into the seed and zero tests were discovered. The agreed kill condition triggered, so the implementation moved to direct xctest.
  4. Eight workers beat “use every core.” Twelve processes inflated suite runtimes by 2–3× under contention; six workers were slower and less stable. Eight was retained after measurement rather than matching the 28-core count.
  5. Retries were not accepted as the primary codemap fix. Instrumentation traced the codemap failures to over-strict ancestor metadata checks. The production invariant was narrowed precisely, then verified with deterministic tests. Retries remain only as visible containment for residual gateway/remote-session process crashes.
  6. The bridging-PCH idea was rejected. Removing -disable-bridging-pch left clean builds essentially unchanged (164.8s vs 165.1s) and made incremental builds 34.9% slower in wall time with 57.2% more CPU. The flag was restored.

Operational expectations

What changes for day-to-day development

Normal builds

Continue using make dev-build. The default path remains fully verified and should settle near the measured ~9.9s warm no-change floor on the profiled machine.

Tight inner loop

Use make dev-build FAST=1 only after a default build has created the verified fingerprint baseline. Changed inputs automatically fall back to full verification.

Fast full-suite feedback

Run unfiltered make dev-test-parallel. It needs no prior ticket, builds the root test artifact from a stable source snapshot, runs it in parallel, and rechecks provenance before recording a compatible ticket.

Contribution evidence

An unfiltered green make dev-test-parallel is full-root contribution evidence. Any FILTER is filtered evidence only. Serial make dev-test remains the supported focused iteration path and fallback.

Important scope rule: a filtered parallel result never satisfies full-root PR-ready evidence. Exit 67 means source/artifact provenance could not be proven and the old ticket remains invalidated.

Residual limitations

  • Across the 10 acceptance runs, 19 suite-level crash/timeout retries occurred and all recovered on attempt two. Most were in RemoteAgentSessionTests and GatewayOpenWorkspaceTests.
  • The parallel result is measured locally on the M3 Ultra. Hosted CI speedup is unknown until measured on hosted runner hardware.
  • Real source-edit incremental builds remain around 16–17 seconds; the large single Swift module is still the structural limit.
  • The implementation and this report are currently uncommitted.

Action items

What needs your decision

No action is required to use the improvements locally. The commands are already present in the current working tree. The following items are maintainer decisions rather than blockers.
  1. Use the promoted parallel lane for full-root evidence. It passed the 10-green gate and now validates source and artifact provenance in one job. Keep serial make dev-test as the focused iteration path and fallback.
  2. Commit the performance changes separately. The tree also contains unrelated quick-model planning changes in AGENTS.md and docs/context/plans/, plus two Oracle prompt exports under prompt-exports/; they are not part of this implementation and should not be staged with it.
  3. Before committing, follow the contribution gate. Stage only the intended implementation/report files, read the contribution-check skill, and run .agents/skills/rpce-contribution-check/scripts/preflight.sh commit after the final staging change.
  4. Optional follow-up: investigate residual gateway/remote-session crashes to reduce retry noise. They did not prevent the acceptance gate, but eliminating them would improve predictability.
  5. Optional future work: profile a module split only if real source-edit rebuild time becomes the next priority. The cheaper PCH alternative was measured and correctly rejected.
