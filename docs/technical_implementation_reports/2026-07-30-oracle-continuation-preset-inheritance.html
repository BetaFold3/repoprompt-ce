Executive summary

The reported bug was real: the two initial Oracle consultations used the intended presets, but a later OracleB critique continued the correct OracleB conversation using OracleA’s model. The result metadata honestly reported model_selection: automatic, revealing that the conversation and the model preset had drifted apart.

The first implementation added a durable preset identity to each Oracle chat and inherited it whenever a continuation omitted model. A real restart test then exposed a second boundary: saved chats also carried an ephemeral provider runID, and the old owner check incorrectly required that run ID to survive an app restart. The final implementation treats the durable Agent session ID as the authority for session-owned chats, keeps exact-run ownership for headless lanes, advances the run stamp after a safe explicit continuation, and lets oracle_chat_log recover same-session history read-only across restarts.

The combined result preserves exact preset identity through full and lightweight persistence, explicit chat_id continuation, Context Builder follow-ups, controller rotation, and app relaunch. Cross-session adoption still fails closed, while model-selection provenance remains visible as explicit, inherited, or automatic.

Current readiness: the focused restart suites, strict lint, authoritative test listing, both product builds, the complete conductor self-test, and the user-visible save/restart/restore matrix are green. The user verified both Oracle lanes, read-only log recovery, inherited continuation after relaunch, deliberate migration, cross-session rejection, and prevention of implicit stale-lane adoption. A separate debug-app assertion crash was recorded earlier, but it did not recur during the successful final matrix and its stack is in unmodified Agent transcript-retention code.

Problem and root cause

Observed symptom

OracleA and OracleB opened correctly. OracleA’s critique stayed on OracleA. OracleB’s first critique continuation used OracleA even though the call supplied OracleB’s chat_id.

Why it happened

The send path selected a model before resolving the target chat. With no explicit model, it chose the first available compatible preset, then attached that model to the requested conversation.

What can we expect from this change?

Explicit chat continuation stays on its lane

Calling ask_oracle with OracleB’s chat_id and no model resolves OracleB’s recorded preset and returns model_selection: inherited.

Explicit switching remains possible

Passing a different preset together with chat_id deliberately migrates that conversation. The new preset becomes the durable binding for later continuations.

Binding and ownership survive reloads

The exact preset UUID and durable Agent session owner are encoded in full chat sessions and lightweight headers. A same-session caller may explicitly continue the lane after its process run changes; the new run stamp is then persisted.

Several unsafe states fail closed

Different Agent sessions, foreign headless runs, deleted presets, mode incompatibility, unavailable models, unresolvable model definitions, and ambiguous legacy model matches return a useful error instead of choosing another lane or preset.

Saved history is recoverable without mutation

oracle_chat_log can read a stale-run lane belonging to the same durable Agent session and echoes its chat_id. Reading the log does not claim or re-stamp the lane.

Implicit restart adoption is intentionally avoided

After restart, a model call that supplies neither chat_id nor new_chat:true does not silently adopt a stale-run lane. Recover the ID with oracle_chat_log, then continue explicitly.

Important policy boundary: fail-closed inheritance applies while model presets are enabled and a specific recorded binding is expected to remain usable. If presets are globally hidden or temporarily disabled, RepoPrompt intentionally uses the single configured planning model and rebinds the chat to it. After presets are re-enabled, pass an explicit model once to move the lane back to the desired preset.

How the fix works

1. Persist one exact lane identity

ChatSession.lastSendModelPresetID stores the exact ModelPreset UUID used by the most recent preset-backed send. It travels with the existing raw model ID and display name as one attribution unit.

2. Resolve the continuation target before selecting a model

For an explicit chat_id continuation with no model override, the MCP path performs a read-only chat lookup first, applies the same tab and Agent Mode ownership checks, and captures that chat’s attribution. For an implicit continuation—neither chat_id nor new_chat:true—the same helper identifies the exact active/latest eligible chat that the authoritative mutation path will resume.

3. Apply a three-tier inheritance strategy

  1. Exact preset UUID: authoritative when present.
  2. Legacy raw model ID: accepted only when it maps uniquely to an available preset.
  3. No attribution: a chat with earlier messages fails closed when multiple presets make its history ambiguous; a never-sent chat may still use automatic selection because it has no historical lane to preserve.

4. Record the selected identity when the send is reserved

sendMessage now accepts overrideModelPresetID. Once the send has passed availability, busy-session, and concurrency checks, it records model ID, model display name, and preset ID together.

5. Preserve identity in Context Builder-created Oracle chats

The Context Builder follow-up resolver now returns the exact model-preset UUID alongside the raw model and chat preset, and the newly created Oracle chat records that binding on its first send. Later chat_id continuation therefore inherits the same preset instead of falling back to raw-model matching.

6. Make durable session ownership authoritative

For an Agent-session-owned chat, agentModeSessionID is the authorization boundary. The run ID is treated as ephemeral metadata: a matching session may continue under a new run, while a different session still cannot adopt the lane. A run-owned-only chat—used by headless or Context Builder flows—continues to require its exact originating run.

7. Load first, then advance the run stamp

Persisted chats may initially exist only as lightweight list stubs. Continuation therefore loads or activates the full session before applying the new run stamp. Stamping first would be unsafe because hydration would replace the in-memory stub with the older disk copy and silently restore the stale run ID.

8. Keep recovery read-only until an explicit send

oracle_chat_log ranks exact-run lanes first, then stale lanes from the same durable session, never foreign or agent-owned lanes for an ownerless caller. It returns history and the resolved chat_id without changing ownership. The later explicit continuation performs the re-stamp.

9. Report selection provenance

"model_selection": "explicit"   // caller supplied model
"model_selection": "inherited"  // chat supplied its binding
"model_selection": "automatic"  // selection fallback

This makes a wrong-lane regression observable without inferring it from prose or model style.

Major decisions and why

Preset UUID, not display name

Names and display labels are mutable and can collide. UUID is the durable identity; display name remains error/UI text only.

Explicit override means deliberate migration

model + chat_id is preserved as a supported operation rather than rejected. After the send starts, future model-less continuations inherit the new preset.

Last send wins

A normal UI or planning-model send cannot prove an exact preset identity, so it clears the exact binding rather than leaving stale attribution behind.

Fail closed instead of “best effort”

Where history indicates a lane identity but that identity cannot be safely resolved, an actionable error is preferred over silently using the first preset.

Backward-compatible persistence

The new field is optional. Existing session JSON without it still decodes, then follows explicit legacy-resolution rules.

Global preset mode is a deliberate escape hatch

Globally hiding or temporarily disabling presets changes selection to the deterministic planning model instead of making bound chats unusable. That send clears the preset UUID and honestly rebinds the lane; restoring a named preset requires one explicit model call.

Session identity dominates run identity

For normal Agent Mode lanes, the durable Agent session is the owner and the provider run is only a replaceable stamp. This is the minimum relaxation that permits restart recovery without allowing a different Agent session to adopt the chat.

Headless lanes remain exact-run scoped

A lane with no durable Agent session ID still belongs only to its originating run. The restart fix does not turn a short-lived Context Builder or headless lane into globally resumable state.

No silent stale-lane adoption

Implicit sends with a current run resume only exact-run lanes. Restart recovery is deliberate: inspect or recover the saved lane through oracle_chat_log, then pass its explicit chat_id.

Read before write

Log recovery is read-only and never changes the run stamp. Ownership metadata advances only when the same durable session explicitly continues the chat.

Prompt and implementation must agree

Tool descriptions and Agent Mode prompts now explain that a returned chat_id carries the lane preset, that an explicit model intentionally switches it, and that results disclose explicit, inherited, or automatic selection.

Review findings addressed

Dual-Oracle review outcome

OracleA and OracleB reviewed the preset-inheritance implementation independently, with exact identities verified, then cross-critiqued the material gaps. After the user’s restart test exposed the owner mismatch, both Oracles also reviewed the restart diagnosis and the proposed session-dominant contract before implementation. The work was extended where their findings identified a real safety boundary rather than documenting the limitation away.

Resolved: implicit resume within one run

A call with neither chat_id nor new_chat:true identifies the authoritative exact-run session and inherits its preset. Across a restart, it intentionally starts fresh instead of guessing which stale lane to adopt.

Resolved by explicit policy: global preset mode

Globally hiding or temporarily disabling presets intentionally selects the deterministic planning model and rebinds the lane. Per-preset deletion, mode incompatibility, unavailability, unresolvable models, and ambiguous legacy matches still fail closed.

Resolved: unattributed history

Historical chats with messages and no recoverable attribution fail closed when several presets are possible. Empty, never-sent chats remain eligible for honest automatic selection.

Resolved: Context Builder identity

resolveMCPFollowUpModel now returns the exact model-preset ID and the Context Builder runner records it in the created Oracle chat.

Resolved: UI sends and stale bindings

A manual UI or other non-preset-backed send records its own raw model attribution and clears the old preset UUID at send reservation, preventing a stale preset/model pair.

Resolved: restart ownership

Same durable Agent session plus new run is accepted; different session is rejected; run-owned-only headless lanes remain exact-run scoped.

Resolved: activate before re-stamp

Both reviews highlighted persistence ordering risk. A targeted persisted-stub test now proves the full saved chat is loaded before the new run stamp is applied, so hydration cannot silently revert ownership metadata.

Resolved: ownerless log fail-open

Post-review inspection found that an ownerless oracle_chat_log request could otherwise see an Agent-owned lane. The final policy exposes only genuinely unowned chats to an ownerless caller.

Residual hardening opportunity

The pre-resolution path rechecks that authoritative chat resolution returns the same session ID after model selection. A future defensive refinement could also compare the attribution snapshot immediately before reservation, although normal busy-session rejection already protects overlapping sends.

Known limitations

Risks, limitations, and technical debt

  • Legacy identity is inherently lossy: sessions saved before exact preset attribution may only identify the raw model. A unique matching preset can be inherited; multiple matches fail closed and require an explicit model.
  • Global preset disabling intentionally changes lane identity: this is an escape hatch to the configured planning model, not preservation of the old preset. Re-enable and explicitly select the named preset to restore it.
  • UI sends deliberately reset exact preset binding: once a person sends into the chat using a non-preset-backed UI model, the old lane UUID is no longer authoritative.
  • A narrow attribution race remains a defensive hardening opportunity: session identity is revalidated after async model selection, but the full attribution snapshot is not compared again immediately before reservation.
  • Implicit continuation is intentionally run-local: after restart, callers must recover or retain a chat ID and continue explicitly. This avoids silently selecting the wrong stale lane when one Agent session owns several Oracle conversations.
  • Cold persisted continuation is covered twice: deterministic persisted-stub tests prove load-before-stamp ordering and message preservation, and the final live provider matrix proves the user-visible save, relaunch, restore, log-recovery, and continuation path.
  • Durable identity means the same Agent session: restoring as a new or forked Agent Mode session correctly fails the owner check even if the Oracle chat ID is known.
  • A separate debug-app assertion crash was observed: it is in unmodified Agent transcript-retention code and is not presently linked to this change, but recurrence deserves its own investigation.
  • No migration is required: the optional JSON field preserves compatibility, but old chats without enough attribution may require one explicit model call.
  • No dependencies, database schemas, feature flags, or environment variables changed.
