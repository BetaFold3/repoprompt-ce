What you can expect in the application

Observed in code The panel is mounted beside Agent Mode and uses a Changes | Preview switch. It preserves the conversation’s protected width: wide windows dock the panel, while narrower windows use a trailing overlay instead of crushing the transcript.

A review loop that stays in context

  • Open from the toolbar, View menu, or ⌥⌘0.
  • Review live edits while the agent continues writing.
  • Expand files and hidden context without opening an editor.
  • Mark files Viewed and see when later edits invalidate that state.
  • Jump directly from an “agent wrote this document” banner to Preview.

A panel that follows real workspace structure

  • Each repository or worktree is shown as a distinct ordered group.
  • Every group owns its checkout identity, activity state, capabilities, and base choice.
  • Unavailable agent worktrees never silently fall back to the main checkout.
  • Git offers index controls; Jujutsu degrades to read-only working-copy review.
  • Non-Git roots receive a clear friendly state rather than a broken panel.

Precise staging, not a second Git client

  • File-level controls remain the simplest path.
  • Hovering a safe hunk reveals Stage Hunk or Unstage Hunk.
  • Selectable changed lines gain quiet line controls and a single “Stage selected lines” action.
  • Unsafe structures—renames, copies, binary patches, conflicts, added/deleted files, and truncated diffs—do not pretend partial staging is available.
  • Section moves are never optimistic; the UI waits for authoritative Git refresh.

Documents that are pleasant to read

  • Semi Markdown keeps source markers visible but subdued while applying readable typography.
  • Rendered Markdown provides the familiar clean reading mode.
  • Wiki links, local document navigation, headings, and supported local media stay inside the preview workflow.
  • Rendered HTML blocks scripts by default; Source shows selectable highlighted HTML.
  • Script execution is a one-document, explicit action with tighter navigation rules.
The expected everyday benefit When an agent edits several files and writes a final report, you can inspect the code, selectively stage reviewed changes, search for a symbol or phrase, and read the report alongside the conversation. The implementation reduces application switching; it does not claim measured speed or memory improvements.

How it works, without the internal jargon

Observed in code The implementation separates what Git reports, what the user sees, and what may mutate the index. That separation is the core safety and maintainability decision.

1. ObserveGit status and scoped file events detect repository state.
2. GroupOne repository actor owns each resolved checkout.
3. ProjectRaw diff data becomes files, hunks, lines, and search ranges.
4. ReviewThe UI renders only target- and epoch-matched snapshots.
5. MutateA reviewed token is revalidated inside the Git index lock.

Changes data layer

  • AgentPanelCheckoutResolver translates logical workspace roots and agent worktree bindings into explicit checkout targets.
  • AgentChangesPanelViewModel owns a pool of checkout-local repository actors for the active tab; switching tabs tears the pool down so background tabs own no watchers.
  • AgentChangesRepository combines porcelain-v2 status with lazy patches, search reads, review tokens, refresh events, and serialized staging operations.
  • GitDiffEngine, GitRawDiffFileSplitter, and DiffLineProjector preserve raw bytes for authority while producing rich, Unicode-aware presentation models.
  • AgentChangesPartialPatchCompiler is a bounded pure compiler for selected hunk or line patches; it never reconstructs authority from rendered text.

Preview data layer

  • The Markdown path decorates the original source string, preserving output.string == source in Semi mode so copy/paste round-trips by construction.
  • The HTML path uses a custom repoprompt-preview:// scheme, a non-persistent WebKit data store, content-security policy, network-blocking rules, and a pure navigation policy.
  • Local HTML reads use a one-shot file-descriptor flow with containment checks before bytes are served, avoiding path re-open races.
  • Agent edit payloads are normalized outside the view layer so the “new report available” banner and transcript edit cards agree about document identity.
Why one repository actor per checkout?

It preserves generation fencing, cache ownership, mutation ordering, and watcher lifecycle locally. A single multiplexed actor would serialize unrelated repositories and make it easier for one group’s retarget or failure to corrupt another group’s state.

Why does search not authorize staging?

Search may load patches for collapsed files automatically. Machine-loading a patch is not evidence that a person reviewed it, so search uses a separate cache and never mints the review token required by partial staging.

Major product and architecture decisions

The implementation moved through several consequential choices. These are the decisions a future maintainer should preserve unless the product contract intentionally changes.

1

Use a custom responsive panel, not SwiftUI’s standard inspector

The obvious first option was .inspector(). The chosen custom layout better supports programmatic deep links, per-window visibility, persisted resizable width, font-scaled limits, and a narrow-window overlay while protecting transcript width.

2

Working Tree is the default; vs Base is explicit and first-class

Most immediate review happens against staged and unstaged work. But agents may commit during a session, so vs Base shipped early rather than leaving the panel empty after commits. Base selection is per repository and never silently inferred or fetched.

3

Semi-rendered Markdown is a source decorator, not a lossy renderer

The defining “Xcode-style” experience keeps #, **, backticks, list markers, and quotes visible but tasteful. Styling the verbatim string means a range mistake can miss styling, but cannot corrupt copied Markdown.

4

Agent-written HTML is treated as untrusted content

A plain local WKWebView would expose too much. The final boundary resolves paths inside a permitted document root, blocks traversal and network loads, uses no persistent website data, and disables scripts by default. In scripted mode, external links are cancelled without even showing the browser prompt.

5

Content changes bypass Git-status fingerprints

Editing an already-modified file often leaves porcelain status unchanged. File events therefore bypass the metadata fingerprint gate, invalidate affected patches, and refresh within a bounded batching window. Without this, the most common agent edit could leave the panel stale.

6

Partial staging was deliberately last and byte-exact

Hunk and line staging carries greater index risk than viewing or file-level staging. Phase 3 retained Git’s raw bytes, limited eligibility to ordinary tracked same-path modifications, and made review tokens the only staging authority. Whole hunks replay Git bytes; selected lines alter only patch markers and hunk ranges.

7

Multi-root became grouped, not selected

The earlier root picker hid the workspace’s full state. Phase 3 removed it and shows every resolved checkout in ordered groups, each with an independent base, status, staging capability, worktree identity, and error state.

Major turns from the implementation reviews

Observed in session The implementation was reviewed after Phases 1–2 and again after Phase 3. Lane B found one critical partial-patch edge case; Lane A later ran a fresh adversarial review and seven fix/verification rounds. Both lanes ultimately returned APPROVED.

Finding or turnWhy it matteredFinal resolution
Rename origin escaped represented scope A rename into a workspace root could have staged the deletion of its origin outside that root. Every mutation path is scope-validated; copy origins are observed but never mutated.
Continuous writes could starve refresh A trailing debounce could postpone updates forever while an agent wrote faster than the debounce interval. Batching retains debounce but forces a flush at a bounded maximum age; FSEvents history gaps trigger full resync.
HTML scheme-handler path re-open race A symlink could change between containment validation and file reading. Resolve, descriptor open, path verification, bounded read, and response happen as one operation.
No-newline partial-patch corruption Git could accept a synthesized selected-line patch that glued two lines into index bytes the UI never displayed. No-newline-annotated hunks are whole-hunk-only, with independent compiler refusal and real-Git integration tests.
Pathspec magic changed read meaning A hostile-looking filename could make a diff read and later literal staging operation refer to different files. Every diff read path now sets GIT_LITERAL_PATHSPECS=1, including large stdin path batches.
A→B→A async retarget race Old work could arrive after the UI returned to an apparently identical target and be accepted. A monotonic target epoch fences snapshots, patch keys, gaps, descriptors, and mutation requests.
Review authority could expire while waiting Checks made before a slow status read or lock wait do not prove the same content is still authorized at mutation time. The lease, target epoch, content revisions, HEAD identity, modes, blob IDs, and scoped porcelain identity are rechecked inside the index-mutation lock.
Search top-N and render costs Early path hits could starve better patch matches; repeated sorting and scanning could scale poorly. The cap applies to the merged corpus stream, results are bucketed per row, and selection survives incremental publication.
What “approved” means here It means both independent review lanes found no remaining blocking defect within the supplied scope after their fixes were verified. It does not replace a live visual smoke test, measured performance work, or the repository’s contribution preflight.

How to test and see the effect, step by step

Use disposable repositories for staging tests The panel intentionally mutates Git’s index. Do not begin hunk/line staging experiments in a checkout containing valuable unstaged work.

  1. Build and launch the current source

    From the RepoPrompt CE repository:

    make doctor
make dev-build
make dev-run

    Launching the app yourself with make dev-run is the simplest path. An agent must ask for explicit approval immediately before a visible launch or relaunch.

    Expected setup: Greeting.swift has two unstaged hunks, report.md appears in both Staged and Unstaged, and report.html is untracked.

  3. Open the panel and check responsive behavior

    Open the printed demo folder as a RepoPrompt workspace root, then open an Agent Mode tab. Click the right-sidebar toolbar icon, choose View → Utility Panel, or press ⌥⌘0.

    • The panel offers Changes and Preview.
    • Dragging its left edge changes width; double-clicking resets it.
    • A wide window docks it; a narrow window overlays instead of over-compressing chat.

  4. Review staged and unstaged changes

    Keep Working Tree selected. Expand Sources/Greeting.swift and docs/report.md.

    • Staged, Unstaged, and Conflicts are distinct sections.
    • report.md appears twice with different patches.
    • Unified mode shows old/new line-number gutters.
    • Split mode becomes available when the panel is sufficiently wide.
    • Expand-context controls reveal hidden lines without changing staging authority.
    • Viewed progress changes when you mark a file and becomes stale after another edit.

  5. Try literal in-diff search

    Click inside the panel and press ⌘F. Search for changed hunk, then use Return or ⌘G to advance and Shift variants to go back.

    • Matches span file paths and patch text.
    • Navigation wraps and auto-expands matching collapsed files temporarily.
    • The current result is visually distinct from other matches.
    • Clearing search restores search-owned expansion without collapsing files you opened manually.
    • Search inside the panel does not hijack search when focus is in the transcript.

  6. Stage one hunk, then selected lines

    Hover the first hunk header in Greeting.swift and choose Stage Hunk. For a different safe hunk, select individual changed lines and choose Stage selected lines. Inspect Git after each action: 

    cd "$DEMO"
git diff -- Sources/Greeting.swift
git diff --cached -- Sources/Greeting.swift
git status --short
    • Only the chosen hunk or lines move into the index.
    • Unselected working-tree content remains untouched.
    • The panel waits for authoritative refresh before moving rows.
    • The corresponding Staged row offers Unstage Hunk/selected lines.

  7. Verify stale-review refusal

    Expand and review a remaining patch, then edit the file from Terminal before clicking a staging action: 

    printf '\n// changed after review\n' >> "$DEMO/Sources/Greeting.swift"

    Expected: the reviewed authority is revoked; the panel refreshes or refuses the action instead of staging content that was not displayed under that review token.

  8. Verify vs Base

    Switch to vs Base, explicitly choose main, and inspect the flat comparison. Try Custom revision… with HEAD~1.

    • No base is silently selected for you.
    • Staging controls disappear in read-only vs-Base mode.
    • An invalid revision affects only its repository group.

  9. Read Markdown without leaving the app

    Switch to Preview, find docs/report.md, and compare Semi with Rendered.

    • Semi mode shows readable typography while keeping Markdown markers visible.
    • Copying the entire Semi document reproduces valid original Markdown.
    • The heading outline navigates to “Summary.”
    • [[notes]] opens the linked document within the preview workflow.

  10. Verify the secure HTML modes

    Open docs/report.html.

    • Default Rendered mode leaves the text as Scripts are blocked.
    • An external link requires confirmation only while scripts are disabled.
    • Source mode shows selectable HTML source.
    • After Run scripts → Enable once, the text changes to Local script ran.
    • While scripts are enabled, the external link does nothing and cannot summon a browser prompt.
    • Navigating away and back clears the one-document script grant.

  11. Add a second repository to see multi-root grouping

    Create another disposable repository:

    Add both demo folders as roots in the same RepoPrompt workspace/session context. Expected: Changes renders two ordered repository headers at once, each with its own checkout identity, activity, explicit base, counts, and staging controls. Search for new local line to jump across groups.

  12. Finish with edge states

    • Open a non-Git folder and confirm the friendly state.
    • Use a Git repository before its first commit and verify unborn-HEAD staging.
    • Use an agent-bound worktree and confirm there is no silent main-checkout fallback.
