Claude CLI executable path override

RepoPrompt CE can now pin every local Claude-family launch to one exact executable path, validate it before use, show what actually ran, and fail safely instead of silently finding a different claude.

Outcome in plain language

The original problem was that RepoPrompt CE asked the login shell where claude lived. A user-installed wrapper exposed only through a GUI or LaunchAgent path could therefore be bypassed. The new setting lets the user select an absolute executable path and makes that selection authoritative. Observed in session

Before

  • Claude launches were resolved through automatic shell-first lookup.
  • A wrapper or auth rotator could be skipped if the login shell returned another installation.
  • Settings could probe a different executable-resolution path from Agent Mode.
  • An invalid path could fall through resolution and surface later as an opaque spawn failure.

After

  • The user can choose one exact Claude executable in Settings.
  • Configured launches validate and execute that path verbatim—no shell lookup and no cache fallback.
  • Settings reports the applied state, validation, actual resolved command, and --version.
  • Bad or corrupt configuration produces a typed, actionable error and remains resettable.
Safety property: once a configured path is applied, RepoPrompt either launches that path or reports why it cannot. It does not silently substitute another claude. Observed in code

What you can expect from this change

Coverage
All local Claude-family flows

Interactive Agent Mode, headless discovery, Settings probes, and Claude MCP install/management use the selection. Standard Claude, GLM, Kimi, and custom compatible backends share it.

Compatibility
Automatic stays automatic

An empty setting preserves the existing login-shell-first behavior. Codex and remote-host executable selection remain outside this feature.

Session behavior
New sessions sample changes

Running sessions are not disturbed. An established logical session retains its captured selection across child-process relaunches; a new session or one-shot operation samples the current setting.

Input support
Absolute path with useful sugar

The Apply flow accepts ~/… and local file:// URLs, preserves valid symlink paths, and supports spaces and Unicode through argv-based launching.

Failure behavior
Loud, typed, recoverable

Relative paths, variable expressions, missing files, directories, non-executable files, broken symlinks, and corrupt stored values are identified without fallback.

Diagnostics
Actual command provenance

Local raw-event diagnostics can identify configuredOverride, automaticResolved, or programmaticOverride. Configured timeout hints explain wrapper transparency requirements.

Wrapper contract: a wrapper must exec the real Claude CLI, keep stdin/stdout stream-json transparent, and avoid printing banners to stdout. A wrapper that forks or decorates stdout can still break the Claude protocol.

How the implementation works

The design keeps user preferences out of the low-level process runner. Higher-level Claude configuration captures a typed selection, then process code enforces it.

1 · Capture

Read cliExecutableOverride.claude when creating a Claude session or one-shot operation.

→
2 · Validate

Require an absolute, executable regular file. Preserve a valid symlink path rather than canonicalizing it.

→
3 · Launch exactly

Bypass CommandPathResolver and ResolvedCommandCache; pass the configured path as argv[0].

Core mechanisms

Typed selection and storage

CLIExecutableOverride.swift introduces:

  • automatic(command:)
  • configuredExactPath
  • programmaticOverride(command:)
  • CLIExecutableOverrideStore with injectable UserDefaults
  • Typed CLIExecutableOverrideError cases with a stable message prefix

Strict process gate

CLIProcessRunner validates configured paths before resolution or spawning in both buffered and streaming modes. Results now include the actual resolvedCommand.

A generation token prevents an in-flight automatic run from repopulating a cache entry after invalidation.

Native Claude controller

ClaudeNativeProcessSessionController retains the captured selection, revalidates the same path before every spawn, and emits command provenance in local raw-event records.

Settings state machine

APISettingsViewModel separates draft input from applied state, orders the mutation pipeline, fingerprints probes, and rejects late results from stale or superseded probes.

The Apply pipeline

validate draft
  → persist configured path
  → invalidate the Claude resolved-command cache entry
  → clear the old probe fingerprint
  → force a fresh --version probe

The Settings probe uses the same automatic .preferShell policy as the runtime, eliminating the prior probe/runtime mismatch. The broader Claude/Codex resolution strategy was deliberately left unchanged.

Why stale probe results cannot mislead the UI

Each probe is associated with both the current executable-selection fingerprint and a monotonic generation. The UI only displays a result matching the applied selection, and an older forced probe cannot overwrite a newer result for that same selection. Observed in tests

6

Prove invalid drafts do not overwrite the applied value

7

Prove there is no silent fallback

After the valid path is applied, remove only the temporary symlink, then start a new Claude session.

Expected: the effective state returns to login-shell lookup, the relevant resolved-command cache is invalidated, and a fresh probe reports the automatically resolved command.

Optional: test a real wrapper instead of a symlink

A minimal transparent wrapper should emit nothing of its own to stdout and replace itself with the real CLI:

#!/bin/sh
exec /absolute/path/to/real/claude "$@"

Make it executable, apply its absolute path, and repeat steps 4–8. If it prints a banner to stdout or does not preserve stream-json stdin/stdout, a connection timeout or protocol error is expected.

Major turns and decisions

These decisions explain why the implementation is stricter than a simple PATH setting and why some seemingly smaller alternatives were rejected.

1 · The problem was not solved by switching PATH order

Investigation showed that the captured login-shell environment overrides much of the GUI environment. Merely changing Claude from shell-first to PATH-first would still miss a GUI-PATH-only wrapper in common setups.

Decision: add an explicit exact-path setting and keep automatic mode’s existing behavior.

2 · Exact means exact—no fallback

The previous resolver only short-circuited for a valid explicit path; an invalid one could continue into shell queries and fail later.

Decision: model configured paths as a distinct typed selection, validate before shell/cache/spawn work, and either launch verbatim or throw a typed error.

3 · Capture per logical session, validate per spawn

The duel surfaced a tension between stable active sessions and immediate pickup of setting changes.

Decision: a logical session retains path A across child relaunches, so settings changes do not mutate an active session. The file at path A is revalidated before each spawn, so repairing or replacing that file can recover. Changing A→B requires a new session.

4 · Draft and applied state must be separate

Persisting invalid text would convert a settings typo into a runtime outage and obscure which value is active.

Decision: invalid saves are blocked, the draft remains visibly distinct, and corrupt stored data is surfaced as a resettable error instead of being interpreted as automatic mode.

5 · Diagnostics use the command that actually executed

Predicting a resolved path separately could disagree with the process launch, especially around caches.

Decision: extend runner results with resolvedCommand and include provenance in native process diagnostics.

6 · The command default was removed as a future-proofing guard

A silent command: "claude" default allowed new call sites to compile without choosing a selection policy.

Decision: require every CLIProcessConfiguration call site to name its command explicitly. The compile sweep found all 16 sites were already explicit after earlier wiring work.

7 · Full-suite failures changed the work plan

The first full run exposed 18 failures across 11 unique cases. At the user’s direction, a scoped worker investigated them instead of dismissing them as unrelated.

Resolution: seven stale or broken tests were aligned to already-committed contracts, and four load-sensitive cases received isolation fixes. An attempted fix for the workspace seeded-root race deadlocked and was fully reverted rather than weakening the test.

Alternatives deliberately not taken

  • No CLAUDE_CLI_PATH environment-variable contract.
  • No automatic canonicalization of symlinks.
  • No broad invalidation of CLIEnvironmentCache.
  • No change to Codex resolution behavior.
  • No separate executable setting for each compatible backend.
  • No remote-host override in this scope.
  • No generic Codex/OpenCode/Cursor settings UI yet.
  • No automatic removal of macOS quarantine attributes.

Cache correctness

Invalidation was narrowed to Claude, and cache generations now prevent a successful in-flight automatic launch from restoring a stale entry after invalidation.

Queued streaming launch safety

Configured paths are validated after acquiring the concurrency gate, preventing queued launches from relying on stale pre-gate validation.

Probe ordering

Monotonic probe generations prevent an older forced probe for the same selection from overwriting a newer result.

Error quality and provenance

Path-bearing diagnostics, accurate post-validation ENOENT wording, directory suggestions using the bare profile command, session-retention pins, and emitted provenance tests were added or corrected.

One no-action disagreement

An environment-cache invalidation suggestion was rejected because the approved contract explicitly keeps that command-agnostic cache and avoids its 1–5 second recapture cost.

Risks, limitations, and technical debt

Known debt Managed preferences

A managed cliExecutableOverride.claude value is read as effective, but Settings does not yet disable editing using objectIsForced. There is no repository-wide MDM pattern yet.

Known debt More CLI families

The storage/type design is generic enough for Codex, OpenCode, and Cursor, but their override UI and wiring are not implemented.

Known debt Remote selection

Remote-host sessions intentionally ignore this local setting. A remote executable override would need a separate host-scoped contract.

Latent test risk Seeded-root watcher race

WorkspacePendingSeededRootTests passes in the final suite, but the session recorded a remaining FSEvents/authority race under load. A quick attempted fix deadlocked and was reverted; a deeper watcher/authority seam is still needed.

Operational Wrapper correctness

RepoPrompt validates file launchability, not wrapper semantics, architecture compatibility, Rosetta availability, or downstream interpreter availability. Those failures surface at spawn or protocol initialization.

Operational Quarantine and TCC

The UI warns about com.apple.quarantine but never removes it. Gatekeeper, protected-folder prompts, and other macOS policy decisions remain user-controlled.
