Executive summary

The work turns the already-landed parallel Oracle feature into a trustworthy knowledge-work substrate. The key addition is packet mode: instead of letting each Oracle inherit the active workspace’s files, tree, Code Maps, git context, and meta prompts, RepoPrompt constructs a deliberately sealed request containing only the supplied question/evidence packet, a lean participant system prompt, and that lane’s own conversation history.

The result is not merely “ask two models.” Each response includes machine-checkable evidence about which model and preset ran, whether the packet and system prompt matched the other lane, whether workspace context was excluded, and whether the answer truly completed or was cancelled, preempted, failed, or partial.

What you can expect from this change

What should now work

  • Ask OracleA and OracleB the same self-contained question at the same time.
  • Keep their first answers independent, with no answer-to-answer contamination.
  • Use a lean, tool-free Knowledge Oracle participant profile.
  • Prove both lanes were constructed from the same packet bytes and effective system prompt.
  • Prove the lanes resolved to explicit, distinct model identities before synthesis.
  • Continue a lane for critique without silently changing its model or participant profile.
  • Reject an ordinary workspace chat being adopted as a supposedly clean packet lane.
  • Reject cancelled, preempted, failed, partial, or unknown results from normal synthesis.
  • Produce a durable *.duel.md note in the active workspace through the workflow.

What is not automatic yet

  • The application does not automatically decide whether to run 0, 1, or 2 critique rounds.
  • There is no persisted, restartable duel-run object or dedicated duel UI.
  • Cross-review anonymization is prompt-enforced rather than code-enforced.
  • Web research is not available to the pure Oracle participants; common web evidence must be collected by the orchestrator and inserted into the packet.
  • A packet lane cannot be resumed after app restart because participant bindings are intentionally in-memory and fail closed.
  • The workflow template must be installed in the user workflow directory before one-command use.

Model choice remains configuration, not implementation

Your current pairing—Claude Fable 5 xhigh as OracleA and GPT 5.6 Sol xhigh as OracleB—is appropriate, but no code depends on those names or providers. The harness uses exact model-preset identities and verifies the model identity echoed by each call. You can repoint OracleA or OracleB later without changing the knowledge-harness implementation.

What was implemented

1. Built-in Knowledge Oracle profile

A stable built-in chat preset and stored prompt were added. The preset explicitly requests no file tree, no Code Maps, and no git context, and promotes one stored prompt to the participant system prompt. The prompt tells the model to use only the packet, label general knowledge, expose missing evidence and assumptions, calibrate uncertainty, treat quoted instructions as evidence rather than commands, and avoid identifying its model or vendor.

Compatibility safeguard: the preset is appended last in the built-in list so it cannot become the order-sensitive default for ordinary chat-mode Oracle calls.

2. A true packet-mode packaging path

ask_oracle now accepts context_mode:"packet" plus an optional exact chat_preset. The implementation does not rely on preset settings alone. It branches before normal context preassembly and constructs a message with empty file contents, tree, git diff, and meta instructions.

This stronger design was necessary because normal chat packaging can include selected file contents and authorized git artifacts through paths not completely controlled by the preset’s “none” settings.

3. Fail-closed participant binding

At creation, a packet lane pins its chat preset, resolved model, and model preset. Every continuation is checked against that binding. A model switch, profile switch, ordinary-chat adoption, post-restart continuation, workspace-context send into a packet lane, or continuation after a UI send took over the lane is rejected rather than silently accepted.

4. Trustworthy terminal outcomes

The send path now records a first-write-wins terminal result before finalization waiters wake. MCP replies expose the outcome, optional detail, and whether returned content is partial. This closes a real failure mode discovered during implementation: user preemption could previously look like a successful Oracle answer carrying only truncated or missing text.

5. User workflow and durable specification

docs/spec/knowledge-duel-v1.md is the durable contract. It documents the request fields, receipt semantics, participant binding, adaptive debate protocol, verification gate, limitations, and a ready-to-install Knowledge Duel workflow. The workflow writes YYYY-MM-DD-<question-slug>.duel.md in the active workspace root or conventional notes directory.

Major turns and decisions

These are the decisions that materially changed the design, based on the session record, third-party review, and independent Oracle reviews.

Extend RepoPrompt instead of building a separate knowledge app

RepoPrompt already owns multi-provider Oracle calls, model presets, no-tools participant execution, context packaging, conversation persistence, exports, and workspace-native notes. A separate app would reproduce that foundation while making it harder to carry a synthesis directly into coding work. A separate product only becomes attractive if mobile/web, multi-user collaboration, or large-scale web capture becomes the primary requirement.

The participant profile belongs in ChatPreset, not an Agent Mode role

An Agent Mode “knowledge” role would shape the orchestrator, not the Oracle participants. The smallest correct seam is the existing combination of model preset, chat preset, and one stored prompt promoted to the system prompt. A lean orchestrator role remains optional future work.

The manual pilot was retired as a formal gate

Your years of manually asking two frontier models and synthesizing their blind spots already established the product value. The plan therefore adopted zero rounds by default with adaptive escalation to one or, rarely, two rounds. Future calibration can come from real persisted duel artifacts rather than a separate 20–30-question study.

Detached start/wait infrastructure was rejected

The landed parallel-Oracle work already supports two concurrent sessions with exact correlation and a two-stream cap. A general job registry would add lifecycle, expiry, cancellation, reconnect, and UI obligations without demonstrated need. The chosen design uses synchronous calls plus a stage barrier.

“No context” configuration was not trusted as a seal

This was the most important implementation pivot. Setting tree, Code Maps, and git to none looked sufficient but was not: selected file contents and authorized git artifacts can still enter normal packaging. Packet mode therefore bypasses preassembly. The guarantee comes from the code path, while the preset remains the participant profile.

Cancellation characterization became a bug fix

The plan originally asked only to characterize what callers observe when a lane is cancelled or preempted. Testing found that preemption could be indistinguishable from success. The scope correctly expanded to structured terminal outcomes so truncated output cannot enter synthesis unnoticed.

Participant binding was pulled forward from a future DuelRun

Independent Oracle reviewers identified model/profile drift as a correctness-critical invariant. Because continuations re-resolve model and preset rather than inheriting them from the chat, prompt guidance alone was insufficient. Binding is now enforced in the send path, before a later state-machine feature exists.

A coded DuelRun was deliberately not built

The implementation now enforces or exposes the invariants that could corrupt evidence: packet identity, profile identity, participant identity, lane integrity, and completion state. The remaining prompt-level behaviors—round cap and anonymization—affect answer quality rather than silently changing the evidence. Shipping the workflow first keeps scope proportional while real use informs whether a durable state machine is worthwhile.

Mutation-testing highlight

During hardening, the guard against adopting an ordinary workspace chat as a packet lane was temporarily disabled. The relevant test did not fail cleanly—it hung until timeout—so the test was changed to race against a deadline. This turns a future regression into a fast, legible failure rather than a stalled test run.

Boundaries, risks, and technical debt

Fail-closed limitations

  • Packet bindings are in-memory; app restart requires new participant chats.
  • A UI send into a packet lane invalidates the lane for future packet continuation.
  • Unknown or non-completed terminal outcomes are not synthesizable.
  • Hashes attest to local construction, not remote provider receipt or compliance.
  • Provider truncation finish reasons are not yet separately surfaced under a locally completed outcome.

Pre-existing stream lifecycle debt

  • scheduleFinalizationWatchdog has no initial arming site and is currently inert.
  • The inactivity watchdog arms only after the first text/reasoning event; a provider that emits nothing can hold a slot until UI cancellation.
  • Cancelling an MCP request cancels its waiter, not the provider stream itself.
  • The headless stream registry remains keyed by tab and should be re-keyed before future duel/web work adopts that path.
Ordinary chat is not packet mode. Selecting the Knowledge Oracle preset in the UI does not by itself seal context. The guarantee comes only from ask_oracle with context_mode:"packet".
Web evidence policy: for comparable answers, the orchestrator should collect sources first and give both models the same dated evidence packet. Independent per-model research may improve discovery diversity later, but it makes disagreements harder to interpret.
