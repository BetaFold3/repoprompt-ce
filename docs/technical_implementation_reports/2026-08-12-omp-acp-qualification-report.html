Oh My Pi ACP provider

RepoPrompt CE now has a managed Oh My Pi (OMP) provider. The code and qualification tools are ready. OMP is still hidden from normal users. The last visible-app safety checks must pass before anyone can select it.

Read this first

What is ready: RepoPrompt can start OMP through the Agent Client Protocol (ACP). It can give OMP one RepoPrompt Model Context Protocol (MCP) server. OMP gets model and login support from its own installed command. RepoPrompt keeps control of tools, workspace context, and permission checks.
What is not ready: normal users cannot select OMP yet. The product stays dark. A DEBUG-only smoke path exists for one controlled test. It does not make OMP public.

Important meaning of policyProof=false: direct checks proved ACP transport, the helper process, and a safe synthetic MCP call. They did not prove that a real app-owned run used the expected process-ID route and the full RepoPrompt permission policy. The app smoke test must prove that next.

What changed

1. Managed start command

OMP starts in a reduced mode

RepoPrompt uses a fixed command. Users cannot remove its safety flags in the provider setup.

omp acp --no-tools --no-extensions --no-skills --no-rules --approval-mode yolo

The code also checks that OMP supports the required flags and requires OMP 17.2.12 or newer.

2. One managed tool path

RepoPrompt MCP is injected into OMP

OMP gets the RepoPrompt MCP server through ACP session setup. It does not get its normal built-in tools, extensions, skills, or rules in this profile.

3. New provider support

OMP joins the ACP provider seam

The app has a launch resolver, provider adapter, event normalizer, model polling path, settings diagnostics, model cache, permission binding, and headless adapter for OMP.

RepoPrompt app
Starts one ACP session and sends the user prompt.
→
OMP command
Uses its configured model and login. Built-in OMP tools are disabled.
→
RepoPrompt MCP
Receives tool calls. RepoPrompt applies its own tool and permission rules.

Expected effect after the public gate opens

  • Users will be able to choose OMP as an Agent Mode provider.
  • The model menu will come from OMP ACP model data. The static default item is only Default.
  • OMP will use the model and authentication that are already available in the installed OMP command.
  • Tool cards should show RepoPrompt tool names, not the raw OMP MCP title form.
  • New sessions will work. Session resume will remain disabled until a separate live test proves it is safe.

Key technical decisions

DecisionReasonResult
Use ACP, not a new OMP runtime OMP already has an ACP server. RepoPrompt already has an ACP controller. Less new transport code. The provider uses the same broad path as existing ACP providers.
Use stdio MCP injection OMP accepts stdio MCP entries, and the existing Cursor ACP path already uses this session shape. No new HTTP or SSE transport layer was added. A different transport remains a fallback only if a live test fails.
Keep the start profile fixed A managed tool boundary cannot depend on a user option that can turn safety flags off. Built-in tools, extensions, skills, and rules stay disabled for this provider.
Keep OMP dark in RELEASE Unit and direct transport checks cannot prove a real app-owned permission route. The normal picker stays empty for OMP. RELEASE code keeps a fail-closed start barrier.
Use fresh sessions only ACP capability data alone does not prove safe cross-process session load and MCP re-registration. Resume IDs are discarded. RepoPrompt uses transcript handoff for a new session instead.
Recognize only exact RepoPrompt tool names for duplicate approval Untrusted text must not grant an approval. Unknown requests stay interactive. A raw server name or a substring is not enough.

Observed in code The fixed command is in OhMyPiAgentConfig.swift. The provider injects the MCP server in OhMyPiACPAgentProvider.swift. The headless adapter waits for MCP routing before it sends a prompt.

Major turns in the work

Plan review chose the simple ACP path

Two planning lanes first disagreed about MCP transport. Source checks showed that OMP supports stdio MCP entries and that RepoPrompt already uses this shape for Cursor. The final plan uses that existing path.

Two dark-mode gaps were fixed

Earlier work found two paths that could start OMP while OMP was dark: a saved or MCP-configured OMP selection, and the generic headless-provider factory. Tests now cover both paths. They fail before provider startup.

The live test harness became stricter

Most later review work improved the test harness, not normal provider behavior. It now checks strict JSON, process cleanup, tool-call counts, workspace snapshots, and private evidence output. This makes a pass from the harness more useful.

Final review approved the code, not public release

OracleA and OracleB approved the frozen 29-file closure snapshot with no P0, P1, or P2 findings. This is a code-review result. It does not replace the required visible-app smoke test.

Why this matters: a long review cycle can look like the provider was unsafe. That is not the finding. The cycle made the test path and the DEBUG qualification gate more exact. The remaining risk is the real app-owned path, which code review cannot run by itself.

How to test and see the effect

Part A — repeat the direct checks

These checks use a fresh private scratch workspace by default. They do not launch, stop, relaunch, or switch the RepoPrompt app. Do not pass a real project workspace.

APP_BUNDLE="$PWD/.build/debug/RepoPrompt.app"

Scripts/omp_acp_live_spike.py --app-bundle "$APP_BUNDLE" --phase preflight
Scripts/omp_acp_live_spike.py --app-bundle "$APP_BUNDLE" --phase helper
Scripts/omp_acp_live_spike.py --app-bundle "$APP_BUNDLE" --phase bootstrap
Scripts/omp_acp_live_spike.py --app-bundle "$APP_BUNDLE" --phase cli-prompt --prompt-timeout 60
Scripts/omp_acp_live_spike.py --app-bundle "$APP_BUNDLE" --phase prompt --prompt-timeout 120
Scripts/omp_acp_live_spike.py --app-bundle "$APP_BUNDLE" --phase roundtrip --prompt-timeout 180

Expected result: each command prints OMP ACP live spike passed and gives a private evidence directory. Keep the raw JSON private. Do not add it to Git.

The round trip uses a test-only read-only MCP proxy with one get_file_tree tool. It proves controlled transport. It does not prove the full RepoPrompt permission policy.

Part B — run the next app-owned smoke

Do this only after a fresh explicit approval to relaunch the visible DEBUG app. Do not stop the app that hosts an active chat session. Use a separate app session, macOS user, VM, or machine if needed.
  1. After the required approval, run make dev-run. It uses the coordinated build, package, and launch path for the current DEBUG app.
  2. Verify the current CE debug CLI with make debug-cli-status. If it is not installed, run make install-debug-cli. Use rpce-cli-debug, not rp-cli or rp-cli-debug.
  3. Get the target window ID from rpce-cli-debug -e 'windows'. Use one positive window ID.
  4. Run the no-edit OMP smoke command below. It creates a temporary DEBUG-only qualification lease, proves the supplied OMP model ID, starts one fresh OMP run, and cleans up the exact run on failure.
Scripts/smoke_omp_agent_mode.sh \
  --window-id <positive-window-id> \
  --model-id 'ohMyPi:default' \
  --output-parent /tmp

Expected result: the script must report a clean OMP route. It checks the OMP process and the bundled helper process, raw tool-call count, workspace state, route order, and terminal cleanup. It does not make OMP public and does not enable resume.

Part C — complete the release-only checks

These checks still need a human-operated app session. They are not yet marked as passed.

  • Run one real RepoPrompt MCP tool call. Prove that the expected OMP process ID and the pre-prompt routing policy were used.
  • Test both an allowed and a denied RepoPrompt action. Confirm that the deny stays denied and that no second OMP approval dialog appears.
  • Use a hostile disposable workspace. Include a rules file, project MCP data, extensions, and skills. Confirm that the managed flags make them inert.
  • Keep an approval-gated MCP call open for at least ten minutes. Check that OMP does not time out.
  • Cancel during generation and during a tool call. Also test process failure or end-of-file cleanup.
  • Check visible streaming, tool cards, model selection, and actionable missing-login errors.
  • Run a separate cross-process resume test before enabling resume. Resume is not part of the current public-release gate.

Limits and safety boundary

What the current tests prove

  • The provider uses its fixed OMP command and checks the OMP executable.
  • The provider creates fresh ACP sessions and injects one RepoPrompt MCP server.
  • The synthetic MCP tool call is read-only and leaves its scratch workspace unchanged.
  • RELEASE keeps OMP unavailable and has a source-backed fail-closed start barrier.

What the current tests do not prove

  • A real app-owned run has used expected-PID and pre-prompt MCP routing.
  • A real allowed or denied tool action has no duplicate OMP prompt.
  • A hostile workspace cannot affect OMP behavior.
  • A ten-minute tool call, cancellation, crash cleanup, and visible tool cards work in the app.
Do not flip ohMyPiAvailable yet. The code deliberately keeps OMP unavailable in RELEASE. The app-owned smoke and the release-only checks above are the gate for that later change.

Observed in code AgentModelCatalog.swift sets OMP availability to false outside DEBUG. WorktreeStartupBenchmarkReleaseAbsenceTests.swift checks that RELEASE keeps the fail-closed OMP barrier and excludes the DEBUG-only qualification surface.

Action items for the maintainer

  1. Keep OMP dark. Do not make a public availability change yet.
  2. Keep the current chat-hosting app open. It may be the only active control connection.
  3. When a separate test environment is ready, give fresh approval for one coordinated DEBUG app relaunch.
  4. Run Part B of this report with Scripts/smoke_omp_agent_mode.sh.
  5. Run each Part C release-only check. Record a short pass or failure summary in the active OMP plan. Keep raw evidence private.
  6. After all release gates pass, make one separate reviewed change to enable public OMP availability. Re-run the release-focused validation after that change.

There is no required action for the already committed code. The next action is live qualification, not more provider implementation.
