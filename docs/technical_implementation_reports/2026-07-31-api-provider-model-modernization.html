Executive Summary

The primary blocker is resolved and live-tested

The OpenAI API provider can now represent and run GPT-5.6 Sol in Pro mode. The model picker exposes mode and reasoning-effort choices, the selected configuration survives settings and job persistence, and the request layer sends the correct OpenAI fields. The user completed a credentialed Oracle run and confirmed that it used GPT-5.6 Sol Pro.

Plain-English outcome You are no longer limited to a hard-coded model name with no way to express “Pro.” The app now treats the model, reasoning mode, reasoning effort, streaming capability, and service tier as related but independently preserved choices.
Clarification: GPT-5.6 Pro mode still has reasoning effort OpenAI’s current GPT-5.6 guidance says reasoning.mode and reasoning.effort are independent. Pro does not force or ignore effort; omitting effort defaults to Medium. That differs from older standalone Pro model IDs, which often fixed or restricted effort. The picker now exposes the complete supported ladder—None, Low, Medium, High, XHigh, and Max—under both Standard and Pro.
Clarification: Flex changes processing priority, not the selected model quality Choosing GPT-5.6 Sol (Flex) → Pro → effort still sends the same gpt-5.6-sol model, Pro mode, and selected effort; Flex is an independent service_tier override. OpenAI documents lower cost in exchange for slower responses and occasional 429 Resource Unavailable errors. The user explicitly accepts that availability tradeoff for expensive Pro-powered Oracle runs.

Claude Opus 5 is now supported through two deliberately separate paths. The original user goal is covered by a new pinned Claude Code CLI row that passes claude-opus-5 to the CLI and exposes Low, Medium, High, Max, and XHigh. The separately requested Anthropic API work adds Opus 5 request handling and paginated /v1/models discovery.

Important boundary: API discovery does not populate CLI providers. The Claude Code Opus 5 row was added independently to the CLI catalogs and provider plugin. OpenAI model visibility is combined with trusted local capability metadata; Anthropic API discovery preserves unknown IDs without claiming to infer every future request capability.

User acceptance: the user confirmed a live GPT-5.6 Sol Pro Oracle response and confirmed that the Claude Code CLI picker now exposes Opus 5. The OpenAI smoke test initially continued using Fable 5 XHigh because the active OracleA preset still targeted Fable; updating Oracle Model Presets → OracleA → Models to GPT-5.6 Sol Pro made the intended provider take effect.

How It Works

Live visibility plus trusted capabilities

OpenAI’s /v1/models response mainly answers “can this account see the ID?” and provides only basic model information. It does not reliably describe reasoning modes, effort values, streaming behavior, token limits, or request protocol, so this implementation intersects OpenAI IDs with trusted metadata. Anthropic’s /v1/models response is richer; this implementation now consumes its IDs dynamically while continuing to use reviewed local request behavior for known special cases such as Opus 5.

1. FetchRead visible model IDs from the configured OpenAI-compatible /models endpoint.
2. MatchIntersect exact IDs with built-in or strict local capability metadata.
3. PickShow only supported combinations of model, mode, effort, and streaming.
4. PersistEncode the complete choice into a versioned provider-specific raw value.
5. SendBuild the correct Responses request while keeping service tier and explicit token caps.

Why a versioned raw value?

The app already stores model selections as strings across settings, presets, sessions, and jobs. A provider-specific versioned codec extends that existing persistence seam without introducing a broad data migration.

v1 built-in selection:
openai_api_selection_v1__<model>__<mode>__<effort>

v2 metadata-backed selection:
openai_api_selection_v2__<model>__<mode>__<effort>__<streaming|completion>

Version 2 was added after review because future metadata may allow none or minimal effort and may explicitly disable streaming. Both facts must survive persistence.

Why not just update the SDK?

The original implementation checked the pinned APIs, but did not audit the latest stable SDK tags rigorously enough. A follow-up audit on 31 July 2026 found:

  • SwiftOpenAI: the repository pins commit 1211782 from 13 January 2026. The latest stable release found was 4.5.0 from 10 July 2026. Its Reasoning type still exposes effort and summary, but not reasoning.mode, so upgrading alone would not remove the Pro-mode request encoder. The upgrade is still worth evaluating separately for accumulated fixes.
  • SwiftAnthropic: the repository’s pinned commit b7d030c is exactly release 2.2.2, the latest stable release found. Its source does not expose adaptive thinking, output_config.effort, or a Models API client.

Therefore the narrow local request encoders remain necessary today. An SDK upgrade should be a separate compatibility change rather than being mixed into the model-support fix.

Major Turns and Decisions

How the implementation direction was chosen

1. The problem was reframed from “missing model” to “missing model configuration”

Adding one static string would not represent GPT-5.6 Sol’s mode, reasoning effort, streaming capability, and service tier. The implementation therefore models a configured selection rather than only a model ID.

2. Two planning Oracles challenged the persistence design

One favored provider-specific raw-string codecs; the other initially favored structured settings and protocol changes. Cross-critique converged on a versioned raw representation because it fits the application’s existing storage contracts and avoids a settings/session migration.

3. SDK limitations changed the transport plan

The pinned dependencies could not encode the new OpenAI and Anthropic fields. The team chose focused URL request planners instead of dependency forks, preserving the existing SDK boundary where it remains useful.

4. Implementation was split across three worker lanes

OpenAI/persistence/UI, Anthropic request encoding, and catalog/metadata were developed as bounded non-overlapping tasks. The root session then integrated shared model behavior, settings, recommendations, and tests.

5. OpenAI dynamic fetching was deliberately made conservative

The Pi-style idea of discovering provider models dynamically was retained for OpenAI, but OpenAI’s live model IDs are treated as visibility—not capability truth. Strict metadata prevents the app from guessing request semantics for an unknown model. Anthropic’s richer Models API received its own adapter because its authentication, pagination, and model namespace differ.

6. Review exposed persistence and request-edge cases

Oracle review found that synthesized token defaults, non-streaming selections, minimal efforts, Anthropic sampling, and stream cancellation needed refinement. Those high-priority issues were corrected before this report.

7. Follow-up documentation audit became implemented scope

OpenAI confirmed that GPT-5.6 Pro mode and effort are independent, so None and Max were added under both modes. Anthropic’s documented Models API then became a dedicated paginated discovery lane rather than a future note.

8. A nested runtime probe separated two confusing test failures

The API-key restart loop came from debug secure-storage policy, not provider validation. The missing explicit Claude Code “Opus 5” row came from a separate static CLI catalog; Anthropic API discovery cannot populate it. Keeping those boundaries separate avoided solving the wrong layer.

9. The original Opus goal was clarified as CLI, not API

The initial implementation spent effort on Anthropic API Opus 5 support. After the user clarified the original intent, a dedicated worker added the pinned model to every Claude Code catalog surface and verified that runtime selection passes the exact ID to the CLI. The Anthropic API work remains because paginated API discovery was also explicitly requested as a separate capability.

10. Live acceptance exposed an Oracle preset-routing distinction

The first live OpenAI attempt still used Fable 5 XHigh because OracleA remained configured for Fable. After the user changed Oracle Model Presets → OracleA → Models to GPT-5.6 Sol Pro, the Oracle run used the intended OpenAI API model successfully. This proved the provider implementation while also revealing that explicit per-call native ask_oracle model targeting remains a separate routing limitation.

2

Choose a launch route, then configure OpenAI

A normal ad-hoc or auto-detected make dev-run may intentionally use process-local secure storage, so an API key disappears when the app exits. Saving a valid key is designed to refresh provider models live; discovery itself should not require a restart.

If you possess an Apple Development identity for the repository’s expected team, use the signed debug route:

SIGN_IDENTITY="Apple Development: Your Name (648A27MST5)" \
DEBUG_SECURE_STORAGE_BACKEND=keychain \
make dev-run

If you do not have that team identity, use the supported persistent local-production install:

CONFIRM_LOCAL_PRODUCTION_INSTALL=1 make dev-install-local-production

The local-production command builds the current checkout under /Applications with a dedicated certificate trusted only on your Mac. It is local-only and not for redistribution. If you ask an agent to launch, relaunch, stop, or install a visible app, the repository rules require fresh approval at that action boundary.

  1. Open Settings → API Providers → OpenAI, configure the key and intended endpoint, then save/validate it.
  2. Let the live model refresh complete; do not restart merely to refresh the list.
  3. For the general planning choice, open Settings → Agent Models → Oracle Model. The equivalent Agent Mode shortcut is the bottom-bar brain button Models → Oracle / Plan Model.
  4. If the active MCP route uses a named preset, also open Settings → Oracle Model Presets → OracleA → Models. A preset left on Fable continues to use Fable even when GPT-5.6 is available elsewhere.
  5. Under OpenAI, confirm GPT-5.6 Sol, then confirm Standard/Pro and None/Low/Medium/High/XHigh/Max.
  6. Select GPT-5.6 Sol → Pro → Medium for Pro with the API’s default effort, or intentionally choose another effort.
  7. Choose GPT-5.6 Sol (Flex) only when slower, lower-priority processing and occasional capacity errors are acceptable; this does not select a lower-quality model.
  8. Save, close the settings view, and reopen it.

Expected: the same configured model, mode, effort, and service-tier choice remain selected after reopening.
